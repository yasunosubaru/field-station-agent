# 00A 总体架构与复现路线

> 本文件只做**地图**：套件由什么构成、谁调谁、按什么顺序启动、每个子系统的文档在哪。
> 细节一律以对应子系统文档为准，冲突时以子系统文档（带 `文件:行号`）为胜。

## 1. 套件构成

`Components.json` 是**功能开关**，决定 UI 里出现哪几个「应用」： `[观察] 01_解包/app/Components.json`

```json
{"components":{"setupmonitor":1,"playback":1,"convert":1,"grit":1}}
```

| 组件 | 中文名 | 实现位置 | 说明 | 文档 |
|---|---|---|---|---|
| **Manage**（setupmonitor） | 设备管理 | `view/js/*`, `view/*/` | 连接接收机、状态瓦片、配置面板、终端、事件、固件升级 | `01_Manage主界面与视图层.md`、`02_配置类视图.md` |
| **Playback** | 日志回放 | `controller/playback.js` + `view/playbackcontrol/` | 打开 .gps/.nov/.sbf 等文件，按时间轴回放 | `04_Playback组件.md` |
| **Convert** | 格式转换 | `view/convert/` + `edie-node-wrappers.node` | 9 种输出格式，含 CLI 模式 | `03_Convert组件.md` |
| **GRIT Monitor** | 干扰监测 | `view/GRIT/` | 频谱、信号矩阵、缓解建议、欺骗检测、地图与 POI | `05_GRIT-Monitor.md` |
| **Graph** | 后处理绘图 | 独立 Electron 应用 `Graph/` | 16 张图表、地图、时间轴、导出 HTML/PDF/KML/CSV | `06_Graph应用.md` |

两个**原生层**支撑上面全部组件：

| 原生层 | 文件 | 作用 | 文档 |
|---|---|---|---|
| Edie / PIMTP | `Edie/pimtpaddon.node`(5.8 MB)、`edie-node-wrappers.node`(3.5 MB) | Longhorn(PIM222) 私有协议解码、NMEA 解码、RINEX 转换、配置读写 | `08_Edie原生解码层.md` |
| 独立工具 | `tosrec.exe`、`datablk.exe`、`rnx2crx.exe` | SREC 转换 / 数据块封装（Longhorn 配置下发）、RINEX 压缩 | `03_Convert组件.md`、`08_Edie原生解码层.md` |

## 3. 启动时序（到「能用」为止）

```
app.on('ready')                     main.js:156
 └─ createWindow()                  main.js:78
     ├─ 读 <userData>/userSettings.json（不存在则不读）      main.js:88-91
     ├─ new BrowserWindow（工作区尺寸，最大化）               main.js:81,92-95
     ├─ win.loadURL(view/html/index.html)                   main.js:102
     └─ ready-to-show → maximize + show                     main.js:128-132
          │
          ▼
   index.html 依次加载 60+ 个 <script>（顺序即依赖，见 00_…md §2）
          │
   $(document).ready                          index.html:1111
     ├─ serverModel.isMapSupported()? 决定是否显示检查更新    :1112
     ├─ 读 Components.json → deviceManagement.setNASComponents :1116-1119
     ├─ $('.welcome-layout').load('./welcome.html')          :1121
     ├─ $('.setUpMonitor-layout').load('./setUpMonitor.html') :1123
     │    └─ 回调里按 Components.json 决定是否 load playback.html / convert.html
     │    └─ 若存在 view/GRIT 目录 → 注入 20+ 个 GRIT 脚本并置 gritSupported=true  :1126-1171
     ├─ deviceManagement.readDevicesData()                   :1180
     ├─ 装配消息目录（OEMSTAR/OEM6/OEM7/SMART2/GIII + tweaks） :1182-1198
     └─ jarvisInterface.loadLanguageData()                   :1199
          │
   硬编码 4000 ms 后切屏：隐藏 splash → 显示 welcome           index.html:1077-1110
   ⚠ 这个 4000 ms 与 `.load()` 的完成没有任何同步信号——是真实竞态（见 01_…md §2）
```

点「Manage」后才会创建连接页；点设备瓦片 → `jarvisInterface.newConnection(tab, connectionDetails)` →
`controller.openConnection` → 收到 `VERSIONB` 且型号识别成功 → `connectionReady[tab] = true` →
`requestInitialLogs` → 逐条 `LOG` 请求。见 `00_通信协议与调度核心.md §6.1`。

## 4. 数据流（一条日志的完整旅程）

```
socket/serial/文件
   │ bytes
   ▼
controller.openConnection 的 data 回调            communication.js:52,194,285
   │  ├─ PingPongHandler.setPingPongCounter(tab,0)  ← 任何入站数据都算心跳
   │  └─ handleLivePlaybackData(data, tab)          ← GRIT live→playback 时改走缓冲
   ▼
GenericParser.processMessage_(data, tab)          genericparser.js:13
   │  半包缓冲 → 找最早记录起点（0xAA/#/%/</[/$）→ 切帧
   ▼
jarvisInterface.logBuffer(msgID, dataview, tab)   jarvisInterface.js:3395
   │  回放时补时间戳 / GIII 分流 / 日志落盘 / 事件总线
   ▼
jarvisInterface.logProcess(msgID, data, tab)      jarvisInterface.js:3822
   │  dummyJSON 命中？→ logParsers.parseData（按 schema 逐字段解码）
   │  → 深拷贝两份，分别投给 GRIT 与 SM 两个视图
   ▼
smlogProcess(msgID, logData, data, tab)           jarvisInterface.js:3922
   │  按 msgID 大分支公式化处理（单位、枚举、派生量）
   ▼
emitter.emit('positionStatus' | 'statusBar' | 'deviceInfo' | 'constellation*' | …)
   ▼
各瓦片组件（positionStatus.js / statusbar.js / …）更新 DOM
```

关键事实：**UI 组件从不碰字节流**，只订阅 `emitter` 事件；解码全部集中在一个 `parseData` switch 里。
`[观察] 00_通信协议与调度核心.md §6.2`

## 8. 跨子系统缺陷清单（复现时必须决定「照抄」还是「修正」）

| # | 缺陷 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| D1 | GPS→UTC 闰秒硬编码 18 s | `jarvisInterface.js:3575` | 2017 年前的数据时间戳偏差 1–9 s | 修，但保留 `gpsToDateMirroring` 供对照 |
| D2 | GPS 纪元串 `'January 6, 1980 00:00:00'` 按**本地时区**解析 | 同上 | 内部 Date 偏移一个时区；显示用本地 getter 恰好抵消 | 修（用 UTC），回放 seek 的 18 s 误差一并修 |
| D3 | 二进制包只判 CRC 字段是否为 0，**从不校验 CRC** | `genericparser.js:139-141` | 坏包会被当好消息解析 | 默认照抄，提供 `validate` 开关 |
| D4 | `fill_command_request` 无 `boolean` 分支 | `frameCommand.js:101-138` | `RTKANTENNA` 的 bool 参数只占位不写 | 照抄并告警（改动会导致设备行为变化） |
| D5 | `events.js` 导出时 `splice(0,-1)` 删掉时刻 | `events.js:300-302` | 导出文件名出现 `YYYY.MM.DD undefined` | 修 |
| D6 | `featuresList.js:1181` 用 `featureStatus` 比较 `"RADIO_TX"` | `featuresList.js:1181` | 无线电发射能力恒判否 | 需实机确认后修 |
| D7 | 语言切换不可达（锚点被注释 + `welcome.js` 重置为 english） | `index.html:275`、`welcome.js:44-46` | 本版实际只有英文 | 修 |
| D8 | `isLuciadAvailable()` 恒 `false` | `index.html:1066-1070` | LuCIAD 地图分支是死代码 | 保留开关，默认旧版地图 |
| D9 | `CalculateCrcResponse` 是半成品（恒 `return 0`） | `crc.js:90-144` | 无人调用 | 不实现 |
| D10 | **心跳负载不是十六进制**：`sendhex` 的 `data` 写死 `"Sendhxdt"` + `length:6`，而手册要求 hex 串 | `pingpong.js:12-27`；真机 2026-10-30 实测 `SENDHEX USB3 6 Sendhx` → `ERROR:Invalid Message. Field = 2` | 心跳从未生效；断链只能靠"收到任意数据"清零 | 默认镜像；`heartbeat.payload` 可改成手册形式 `14 3A B5 90 0D 0A` |

## 9. 未解之处（跨文档汇总）

1. ~~**心跳负载**：`SENDHEX` 实际发什么字节未验证（代码里像占位符 `Sendhxdt`）。见 `00_…md §9.1`。~~
   **已解（2026-10-30，OEM729 真机）**：手册要求 hex 串，`Sendhxdt` 被接收机拒（`Field = 2`）；
   真实六字节为 `14 3A B5 90 0D 0A`。记入 `00A §8 D10`。
2. ~~**`_28` / `_29` 虚拟端口语义**：只按数字分类，未对照手册 Table 6 确认。见 `00_…md §9.2`。~~
   **已解（2026-10-30，OEM729 真机）**：真机 `LOGLIST` 里 `USB1_29` / `USB2_29` 正在使用，
   内容与抓到的二进制流逐条对应；28/29 是套件自选的虚拟组号，不是手册常量。
3. **GIII 二进制头与时间字段**：回放里按 OEM 偏移硬读，GIII 真实布局未知。见 `04_…md §9`。
4. **Graph 的 `EncryptionKey` 派生算法**：在 8.8 MB 原生模块内。见 `06_…md §9`。
5. **Convert 的 9 种格式编解码**：全在原生模块里，纯 JS 复现需要逐格式重写。见 `03_…md §9`。
6. **GIII CARDSTATUS 卡记录重叠**：偏移 20–76 但步进 60。见 `00B_…md §9`。
7. ~~**`FILEROTATECONFIG.maxFileSize` 单位**：硬编码 4096，单位未知。见 `02_…md §9`。~~
   **已解（2026-10-30，手册 §2.50）**：`MaxFileSize` 单位 **MB**、`MaxFileTime` 单位小时，
   默认 `0 4096 STOP`；且该命令不支持 OEM719/729。
8. **帮助系统锚点映射**：`help.js` 1.34 MB 未全文映射。见 `01_…md §9`。
