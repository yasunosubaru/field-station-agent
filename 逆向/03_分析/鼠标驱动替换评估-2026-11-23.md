## 0. 先纠正一个前提：我们现在**不在用** `SetCursorPos + mouse_event`

用户描述的三级升级是「语义（CDP element.click）→ 真鼠标（SetCursorPos+mouse_event）→ 坐标」，
但按当前源码，这个描述有一处关键偏差：

- **`SetCursorPos + mouse_event` 是已经废弃的历史尝试，不是现行代码路径。**
  它只作为失败记录写在 `src/fieldstation/workflows/runner.py:1290-1293` 的 docstring 里：
  `window.screenX` 在无边框 Electron 窗口报 `(0,0)`，算出的坐标落到别的窗口（OpenChamber），
  `WindowFromPoint` 当场抓到。[源码]
- 现行所有"真鼠标"步骤**统一走 CDP `Input.dispatchMouseEvent`**（视口 CSS 坐标），
  不经 Win32、不受窗口位置与遮挡影响。[源码]

这个偏差直接决定了后面的判断：agent-desktop 的 `--headed` 如果等同于 OS 级物理输入，
它对标的是我们**已经放弃的那条失败路径**，而不是我们现在的 CDP 路径。

## 1. 现状盘点

### 1.1 入口分派（`src/fieldstation/workflows/runner.py`）

|---|---|---|

### 1.2 三级升级链的真实层级（`tools/click_engine.py`）

`CdpDriver.escalating_click()` (`cdp_driver.py:347-379`) 调用
`ClickEngine.click_escalating()` (`click_engine.py:369-430`)：

| 级 | `escalation` 值 | 定位方式 | 点击方式 | 代码位置 | 触发条件 | 已知缺陷 |
|---|---|---|---|---|---|---|
| L0 | （无标记） | 文字 / `target:` | `_click_js()` → `el.click()` | `cdp_driver.py:393-409`, `_CLICK_JS` `:488-521` | 普通 `click` 且没有 `css` | JS 合成事件：不发 `pointerdown/mousedown`、不触发 `:hover`、不更新焦点、被遮挡也"成功"；**不触发 Electron 原生对话框**。[源码 + 用户实测] |
| L1 | `semantic-realmouse` | `collect()` 池（`cursor:pointer` + 语义标签）+ `pick()` | `Input.dispatchMouseEvent`（真鼠标语义） | `click_engine.py:216-252`, `:399-409` | 默认第一级 | 语义池会漏元素（实测同一页语义选择器 4 个 vs `cursor:pointer` 48 个）；CDP 事件不构成 Electron IPC 要求的真实用户手势。[源码 + 文档] |
| L2 | `coord-signature` | CSS 选择器 → `getBoundingClientRect` 中心点 | 同上 + `elementFromPoint` 命中签名校验 | `click_engine.py:333-366`, `:411-426` | L1 抛 `ClickError` / 异常且给了 `css` | 布局一变就漂移（靠 `record_coords()` 重标定）；仍不改变手势性质。[源码 + 文档 §9.4] |
| L3 | — | — | 抛出带全部失败原因的 `ClickError` | `click_engine.py:430` | L1、L2 都失败 | — |

注：源码注释明确说 **"第 1 级已经是真鼠标"**（`click_engine.py:393`），
所以三级不是"语义 → 真鼠标 → 坐标"，而是"语义定位的真鼠标 → CSS 定位的真鼠标 → 报错"；
真正的 JS `el.click()` 是链路外的 L0。[源码]

### 1.3 `_real_mouse_click` 的特别之处（`runner.py:1283-1380`）

它是唯一为"必须真实用户手势"场景设计的通路，做三件事：

1. 用 `getBoundingClientRect` 取视口中心点，`elementFromPoint` 确认中心命中自己（遮挡则报 `selector_drift`）；[源码]
2. 用 CDP `Input.dispatchMouseEvent` 发 moved / pressed / released（间隔 50ms / 60ms）；[源码]
3. **仅审计不阻断**：用 `window.screenX + vx` 估算屏幕坐标，`WindowFromPoint` + `GetAncestor` 取顶层窗口标题，写进返回值的 `screen_would_hit`。[源码]

第 3 步正是踩坑点：它依赖 `window.screenX`，而该值在无边框 Electron 窗口里报 `0,0`，
所以这个"审计"本身也是不可信的；而且它只记录、不拦截。[源码]

### 1.4 卡了半个月的真正卡点（与鼠标库无关）

- 源码级已确认：Graph 的 Select 调 `window.file.selectDirectoryDialog()`，
  这是 preload 暴露的 IPC，主进程才真正弹 `#32770` 原生目录对话框。[用户实测 / 逆向确认]
  对应 IPC 台账：`逆向/03_分析/06_Graph应用-附录/B_IPC通道清单.md:36`
  `SELECT_FOLDER_DIALOG → dialog:openDirectory → file.selectDirectoryDialog`。[文档]
- JS click 不弹；改 CDP `dispatchMouseEvent` 仍不弹。[用户实测]
- 本仓库**已有绕开原生对话框的成熟做法**：`逆向/03_分析/14_Graph第二份样本.md:384-389`
  的 `graph-second-sample.cjs` 在主进程把 `dialog.showOpenDialog` 换成按点击顺序出队的桩函数、
  在渲染进程覆盖 `window.file.selectDirectoryDialog`；`06_Graph应用.md:960-963` 同样结论。
  这说明"手势问题"可以用**桩函数**解决，而不需要更会点鼠标的库。[文档]

## 2. `agent-desktop` 能不能替

资料来源：npm 包页面 `agent-desktop` 的 README（GitHub 仓库 `vercel-labs/agent-desktop`；
本轮 GitHub raw 抓取失败，以 npm README 为准）。版本 1.3.1，Apache-2.0，
Windows 10 1809+ / x64 或 ARM64，底层用 **UI Automation**。[文档]

### 2.1 它的 click 走哪条路

- **默认 headless**：README 原文 "Headless by default. Ref actions use the accessibility
  API without moving the pointer or taking focus. The global `--headed` flag allows physical input."[文档]
- 即：
  - `--headless`（默认）= **accessibility API 动作**，等价于 Windows UIA 的 `InvokePattern` /
    `SelectionItemPattern` / `LegacyIAccessible.DoDefaultAction` 一类程序化调用，**不移动指针、不抢焦点**。[文档]
  - `--headed` = **OS 级物理输入**，会移动指针、抢焦点。[文档]
- 它不内置模型，只有 CLI / C library / MCP；61 个命令名（57 个可操作），
  含 `mouse-click`/`mouse-move` 这类原始输入命令。[文档]

**与我们的映射**：headless ref click ≈ 我们 `uia_driver.py:205-222` 的 `Invoke-El`（同一个类别）；
headed click ≈ `SetCursorPos + mouse_event`（我们已废弃的历史路径），
而不是现行的 CDP `Input.dispatchMouseEvent`。[推断，类别级；具体 API 调用机制未验]

### 2.2 关键：对"需要真实用户手势的 Electron IPC 对话框"，它能不能救

**结论：救不了。** 两条路分别卡在两处：

| 路径 | 能否触发 `selectDirectoryDialog` 的原生对话框 | 理由 |
|---|---|---|
| headless（默认） | **大概率不能** [推断] | accessibility 动作是程序化调用，不产生 OS 级 pointer 输入，和 `el.click()` 同属"非真实手势"类别；而且见 2.3，它根本看不到这个按钮 |
| `--headed` | 手势层面**可能可以**，但定位层面做不到 [推断] | 物理输入正是 Electron 想要的真实手势，但它必须先把 ref 解析成屏幕坐标；ref 来自 accessibility tree，而我们已实测 UIA 看不到 Chromium 页面内容（见 2.3） |

**会不会有同样的"点错窗口"问题？**

- headless：不产生物理点击，所以不存在"点到 OpenChamber 上"的物理错窗；但代价是它也无法做手势。[推断]
- `--headed`：**同一类风险仍然存在**。`--headed` 走 OS 物理输入，输入落到坐标处最上层窗口，
  遮挡/焦点竞争依然会打错对象。[推断]
  - 一个可能的有利差异：agent-desktop 的 ref 绑定到具体窗口（`--window-id`，README 说
    "Window-owned refs stay pinned to their original window"），且 UIA 元素 frame 是**绝对屏幕坐标**，
    理论上不需要 `window.screenX` 这个会报 `0,0` 的量，能避开我们那个**具体的**算错坐标 bug。[推断，机制未实机验证]
  - 但它会移动指针、抢焦点，直接破坏我们当前"CDP 派发不动指针、不抢焦点"的性质；
    在固定虚拟屏 + 会话保活的场景里，抢焦点本身可能引发新的绘制/保活问题。[推断]

### 2.3 致命前提：它在 Windows 上读的是 UIA，而 UIA 看不到我们的目标

这是拒绝替换的决定性证据，且来自我们自己的实测台账：

- `docs/operations/rpa-click-engine.md:109-111`：实测（套件 2.11.0）
  **UIA 对 `NASRunner` 只能拿到顶层 Window 一个节点，Control/Raw 视图都没有子节点 → UIA 看不到 Chromium 渲染内容**。[文档]
- `tools/cdp_driver.py:6-11`：即使加 `--force-renderer-accessibility`，本机 Electron 8 的 UIA 树里
  仍只有 `Chrome Legacy Window`，看不到网页控件。[源码]
- `docs/operations/rpa-click-engine.md:232-236`：UIA 擅长原生文件对话框，
  **看不进 Chromium 页面**；页面内容必须用 CDP。[文档]

agent-desktop 的全部价值主张是"读 accessibility tree，给每个元素一个 ref"。
对 Chromium/Electron 页面内容这条路在我们这台机器上是**瞎的**——
它拿不到 Select 按钮的 ref，既做不了 headless 动作，也没有 `--headed` 可点的坐标来源。[推断，由上述实测直接推出]

唯一还能用的是它的原始 `mouse-click` + 固定坐标，但那就退化成"第三方二进制包装的 SetCursorPos"，
相比我们已有的 CDP 坐标路径没有任何增益。[推断]

### 2.4 若强行选 A，迁移代价清单（仅列出，不推荐）

- 引入 npm 原生二进制包（含 x64/ARM64 helper）或 GitHub Release 原生归档，新增第三方依赖与体积。[文档：有原生二进制；体积数字 `[未验]`]
- 仅从源码构建才需要 Rust/Cargo 工具链（README 的 Development 段是 cargo 命令）；用预编译包不需要。[文档]
- runner 驱动协议要加一个 agent-desktop 后端，或在 UIA 分支外包一层；`_step_gui` 的 action 分派要改。[源码]
- `--headed` 会移动指针/抢焦点，与现有"三层几何保证 + 不抢焦点"设计冲突，需重新验证会话保活与绘制。[推断]
- STALE_REF / AMBIGUOUS_TARGET 重试循环要接进 runner 的错误分类，增加一层失败模式。[文档 + 推断]

## 3. 虚拟屏固定 1920×1080 带来的简化

### 3.1 坐标法是不是就可靠了

**"在哪点"这一维：是，已经可靠。** 本仓库实测台账给出完整证据链：

- 三层几何保证：虚拟屏 1920×1080@60（程序化切换 + 读回校验）→ 会话保活 → CDP 视口钉死 `1920×1080`。[文档：`docs/plans/2026-11-15-本机驱动方案.md:352-401`]
- 视口钉死后元素坐标确定：1920×1080 / 1280×800 / 2560×1600 三次采样元素坐标都是 `(100,200)` 精确，
  `devicePixelRatio=1.0`，清 override 再钉结果一致（幂等）。[文档：同上 `:355-363`]
- CDP 点击不被物理窗口裁剪：视口钉 1920×1080、窗口物理只有 800×600 时，视口外 `(1860,990)` 的 `outside` 仍 HIT。[文档：同上 `:365-374`]
- 我们自己的 `fix_viewport()` / `record_coords()` / `click_point()` + `elementFromPoint` 命中签名，
  已经把"钉视口 → 记坐标 → 点前校验"闭环实现，并做过故意挪 200px 被拦住的负例。[源码 + 文档：`rpa-click-engine.md:177-220`]

**但"算不算手势"这一维：几何完全帮不上忙。** Electron 的 IPC 原生对话框要的是 OS 级真实用户手势，
不是正确的坐标。`window.screenX=0,0` 导致的错窗是坐标问题（几何已能解），
而 `dispatchMouseEvent` 仍不弹窗是手势问题（几何解不了）。[用户实测 + 推断]

### 3.2 固定坐标 vs 语义定位

| 维度 | 固定坐标（`click_point`） | 语义定位（`collect`+`pick`） |
|---|---|---|
| 前提 | 视口钉死 + 布局不变 + 点前命中签名 | 元素有可见文字 / aria-label / `cursor:pointer` |
| 优势 | 确定、快、可回放、不依赖 DOM 语义；适合无文字图标块和覆盖层 | 布局变动、弹窗/横幅推移、套件升级改版后仍可用；可读可维护 |
| 风险 | 顶部出现/消失横幅、弹窗改变下方布局、套件升级改版 → 漂移，需 `record_coords()` 重标定 | 语义池会漏（实测 4 vs 48）；同名元素需 `@2` / 面积最大启发式，仍有歧义 |
| 文档依据 | `rpa-click-engine.md:222-230`（明确列出"用/不用"场景） | `rpa-click-engine.md:9-21`、`:37-44` |

### 3.3 判断：固定虚拟屏能否让坐标点击成为主路径

**可以让它成为"定位"的主路径，但不能让它成为唯一路径，更不能让它替代手势通路。**

- 对**布局稳定的已知目标**（固定套件 UI、钉死的 1920×1080 视口），坐标 + 命中签名足够可靠，
  可以优先于语义池，减少模糊匹配歧义。[推断，基于 3.1 实测]
- 但必须保留：① 语义路径用于发现新目标和应对布局漂移；
  ② `elementFromPoint` 命中签名作为强制闸门（否则固定坐标会"稳稳地点错"）；
  ③ 一条**独立的手势通路**专门服务原生对话框——这正是当前最缺、而几何保证解决不了的部分。[推断]
- 所以用户那句"反正都是虚拟屏幕固定大小点"**对了一半**：几何确定性已经把"点准"这件事闭环了，
  卡点从来不是"点准"，而是"点下去算不算真实手势"。[推断 + 用户实测]

## 4. 结论（三选一）

## **选 B：借思路不替换**

**理由（一句话）：agent-desktop 的核心能力是"读 accessibility tree 按 ref 操作"，而本仓库已实测
UIA 看不到 Chromium/Electron 页面内容（只有顶层 `Chrome Legacy Window`），它连 Select 按钮都定位不到；
它的 `--headed` 物理点击又和我们已废弃的 `SetCursorPos+mouse_event` 同属 OS 级输入，
解决不了"真实用户手势"这个真正的卡点——缺的不是更成熟的鼠标库，而是"可信手势 + 正确绝对坐标"。**

### 为什么不是 A

- 不是成熟度的差距，是**感知通道被堵死**：它的 AX/UIA 输入源看不到我们的目标。[文档实测 + 推断]
- 它的 headless 不产生手势，它的 headed 会抢焦点/移动指针，与现有几何+会话保证冲突。[文档 + 推断]
- 引入 Rust 二进制、第三方依赖、STALE_REF 重试层，换不来对卡点的任何改善。[推断]

### 为什么不是 C

- "固定虚拟屏下我们那套已经够用"对**定位**成立，对**手势**不成立：
  CDP `dispatchMouseEvent` 仍不弹原生对话框，这是半个月的实际卡点。[用户实测]
- 所以不能下"已经够用"的结论；要补的是手势通路，而不是替换整个鼠标引擎。[推断]

### 从 agent-desktop 借鉴什么、具体改哪几处（按优先级）

| # | 借鉴机制 | 具体改动位置 | 目的 | 等级 |
|---|---|---|---|---|
| 1 | "真实 OS 手势 + 正确绝对坐标"独立通路 | `runner.py:1283-1380` `_real_mouse_click`：新增 opt-in 的 OS 级 `SendInput` 点击（仅 `real_mouse` action / 原生对话框触发点），坐标用 Win32 `ClientToScreen(hwnd, ...)` 或已知窗口矩形推导 | 解决 `selectDirectoryDialog` 不弹窗；绕开 `window.screenX=0,0` | [推断，需实测] |
| 2 | "ref 钉在窗口上" / `--window-id` 消歧 | `runner.py:1348-1377`：把 `screen_would_hit` 从**只审计**改成**硬闸门**；步骤开始时记录目标 HWND，命中不是它就直接失败，不再静默继续 | 消除"点错窗口" | [源码 + 推断] |
| 3 | 修掉不可信的坐标换算 | `runner.py:1362-1365`：去掉 `window.screenX + vx`，改用已获取的 HWND 做 `ClientToScreen`（DPI awareness 调用已在 `:1359`） | 让审计/新通路拿到正确绝对坐标 | [源码] |
| 4 | snapshot + ref + STALE_REF | `tools/click_engine.py:216-252` `click()` / `:161-198` `pick()`：给 `collect()` 的 `data-fsa-idx` 绑定 `snapshot_id` 并写进 `entry`；点击前校验该 idx 仍存在且 rect/签名未变，否则抛 `STALE_REF`-analog，别悄悄重选一个 | 避免 DOM 刷新后"点中另一个元素" | [推断] |
| 5 | 保留 headless/headed 的显式区分 | 在设计文档里写明：CDP `Input.dispatchMouseEvent` = 我们的 headless（不动指针/不抢焦点），OS 物理点击 = 我们的 `--headed`，只在单个 action 上显式开启，永不默认 | 保住现有几何与会话保证 | [源码 + 推断] |
| 6 | 更彻底但更大的备选 | 参考 `14_Graph第二份样本.md:384-389`：在能控制启动参数时，直接桩掉主进程 `dialog.showOpenDialog` + 渲染进程 `window.file.selectDirectoryDialog` | 从根上消灭手势需求（但要求能注入启动代码，对现成套件未必可行） | [文档] |

### 验证门槛（若实施，必须自证）
