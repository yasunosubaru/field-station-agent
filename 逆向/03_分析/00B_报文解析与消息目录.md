## 1. 职责

本子系统把接收机二进制/ASCII 报文还原成扁平 JSON，供状态栏、位置页、卫星视图、SPAN/对准页、干扰
工具箱、文件与网络配置页消费；同时提供「这台接收机支持什么」的能力判定。

| 模块 | 职责 | 主要出口 |
|---|---|---|
| `logparsers.js` | 字节级报文解析。`parseData` 一个 `switch(msgid)` 一个 case，硬编码每个字段的偏移、类型与枚举映射 | `parseData`、`parseGIIIData` |
| `NovatelIdConstants.js` | 全部常量：消息 ID 表 `messageIdConstants`、枚举表、端口/机型/信号表、`MessageHeaderLength=28` | 全局对象 `NovatelIdConstants` |
| `featuresList.js` | 由 `VERSION` 日志的 `model` 字符串 + 硬件版本 + 许可特性推出星座/频点/定位模式/SPAN/GRIT 能力，按 tab 缓存 | 82 个导出函数（附录 `features-matrix.csv` 90 条判定/取值条目） |
| `MessageIdConstants.js` / `M6MessageIdConstants.js` / `GIIIMessageIdConstants.js` | 三张消息目录表（OEM7 / OEM6·OEMSTAR / G-III），键为 messageId，值为 `Name/Type/Category/CorrectionType` | `M7MessageIdConstants.messageIds`、`M6MessageIdConstants.messageIds`、`GIIIMessageIdConstants.messageIds` |
| `MessageIdTweaks.js` | 对三张表做局部覆写（周期、触发方式、双天线副本、隐藏/改类） | `MessageIdTweaks.messageIds / messagePeriods / messageTriggers / dualAntennaMsgs` |
| `positionModes.js` | 把「已配置的定位模式」和「正在工作的定位模式」两个状态机从报文流里推出来 | `getConfiguredModes`、`getActiveModes`、`getOperatingMode` |
| `ConstellationHandler` / `Constellation` / `gritConstellation` | 把 TRACKSTAT/SATVIS2/BESTSATS 三类解析结果按星座归并，供天球图与信噪图 | `trackStatData`、`satvisData`、`bestSatsData` |
| `bestpos.js`、`satvis2.js` | 两处**旁路**实现：各自独立重写了 BESTPOS(42) 与 SATVIS2(1043) 的读取 | `BestPos`、`satvis2` |

`[观察] 01_解包/app/model/logparsers.js:3102` `parseGIIIData` 是 G-III 的独立入口。

**附录 CSV 的口径**（复现时照此读）：

- `messages-oem7.csv` / `messages-oem6.csv` 的 `parsedByApp` 指「该 id 在 `parseData` 的
  `switch` 里有 case」：OEM7 表 670 行中 108 行为 true，OEM6 表 638 行中 76 行为 true

## 3. 数据结构

### 3.1 字段 schema

每个消息在 `logparsers.js` 顶部有一个 `const xxxJSON = {…}`，形如 `字段名: [类型码, 偏移]`；
需要重复块时再嵌一层对象（键名就是「块」的名字）：

```js
const satvis2JSON = {
  "sats":   { "satelliteSystem":[ENUM,0], "satVisibility":[ENUM,4],
              "almanacFlag":[ENUM,8],     "numberOfSatellites":[ULONG32,12] },
  "system": { "satelliteId":[ENUM,16], "satelliteIdTemp":[UINT_16,16],
              "health":[ENUM,20], "elevation":[DOUBLE,24], "azimuth":[DOUBLE,32],
              "trueDoppler":[DOUBLE,40], "apparentDoppler":[DOUBLE,48] }
};
```

`[观察] logparsers.js:119-125`。全文件共 **113 个这样的 schema 常量**，其中若干是同一消息的两套
互斥定义（见 §5.7）。schema 里的 offset **一律相对于 payload 起点**，读取时由 `getData` 加上
`headerOffset = 28` `[观察] logparsers.js:753`、`NovatelIdConstants.js:13`。

### 3.2 解析结果对象

| 键 | 类型 | 语义 | 来源 |
|---|---|---|---|
| 各字段名 | number / string / `{value,offset}` | 见 §3.3 | schema |
| `tab` | string | 会话标签，**每个返回值都带** | 每个 case 末尾 |
| `0..n`（数字键） | object | 重复块的第 n 条记录（SATVIS2/TRACKSTAT/BESTSATS/ITPSD） | `logResponseData[loop]` |
| `data` | array | 重复块的整体（GGAQUALITY/ITDETECTSTATUS/LBANDTRACKSTAT/SKCALIBRATESTATUS/VERIPOSDECODERSTATUS） | `logResponseData.data = completeData` |
| `noOf…` / `…Count` / `noEntries` | number | 计数回填 | 各 case |
| `sequence` / `sequenceId` | number | 头里 offset 10 的 `UINT_16` | `logData.getUint16(10, true)` |

`[观察] logparsers.js:928, 944, 947`（数字键 + tab）、`logparsers.js:847-849`（data 数组）。

⚠ 同一个消息的不同 case 里，重复块的落点并不统一：ORDER 型用 `logResponseData[n]`，
GGAQUALITY/ITDETECTSTATUS 等用 `logResponseData.data[]`。复现时必须按消息分别处理，不能统一。

### 3.3 `getData` 的返回形态

- 数值类型返回 JS number（`ULONG64` 返回**十进制字符串**，`logparsers.js:663`）。
- `STRING_n` 返回去掉 `\0` 的定长字符串（`logparsers.js:652-661`）。
- `ustringvariable` 返回 `{value, offset}`，`offset` 是**下一个字段的绝对起点**（已 4 字节对齐）
  `[观察] logparsers.js:664-690`。
- 越界返回数字 `0`（不是 `undefined`，也不是异常）`[观察] logparsers.js:625-627`。

## 5. 报文/协议细节

### 5.1 帧结构（由 `genericparser` 决定，解析器只认 payload）

| 位置 | 长度 | 含义 | 依据 |
|---|---|---|---|
| 0-2 | 3 | 同步字 `AA 44 12`（0x12=18）或 `AA 44 13`（0x13=19，短头） | `genericparser.js:25,29` |
| 3 | 1 | 头长：0x12 → 28；0x13 → 12 | `genericparser.js:32,37` |
| 4-5 | 2 | messageId（小端 `UINT_16`） | `genericparser.js:44` |
| 6 | 1 | **message type**，解析器称 `logType` | `logparsers.js:757` |
| 7 | 1 | 端口号 | 未使用 |
| 8-9 | 2 | payload 长度（短头时改在 offset 3 的 1 字节） | `genericparser.js:31,36` |
| 10-11 | 2 | sequence | `logparsers.js:931` |
| 12 | 1 | idle time（byte） | `logparsers.js:768` |
| 13 | 1 | time status | 未使用 |
| 14-15 | 2 | GPS week | `jarvisInterface.js:3571` |
| 16-19 | 4 | GPS 毫秒 | `jarvisInterface.js:3572` |
| 20-27 | 8 | RX status / reserved | 未使用 |
| 28… | len | **payload**，`MessageHeaderLength = 28` | `NovatelIdConstants.js:13` |
| 28+len | 4 | CRC，必须 **≠ 0** 才进入解析 | `genericparser.js:45-48` |

`[观察]` 上述偏移全部来自代码；`[推断]` 「offset 6 = message type、offset 7 = 端口、offset 13 = 时间
状态」是按 `[外部参考]` 的 OEM7 二进制头表补齐的语义，代码只用到 6、10、12、14-19。

CRC 只被当成「是否为零」的开关，**没有做多项式校验** `[观察] genericparser.js:46-48`。
`BESTPOS` 的 schema 里反而把 payload 末尾 4 字节当数据读了：`"CRC":[uhex,72]`
`[观察] logparsers.js:94`。

### 5.2 `logType`（`getUint8(6)`）三条路径

```
logType == 0  → 主 switch，115 个消息 ID（解析器这一支的全部内容）
logType == 1  → 只认 3 个 ID：TRACKSTAT(83) / ITDETECTSTATUS(2065) / ITPSDDETECT(2063)
logType 其它  → 把整包转 hex，正则找 "4F4B"（ASCII "OK"）
                命中 → {Commanddata: OK}；否则 → {Commanddata: ERROR, ErrorMessage: hex}
```

`[观察] logparsers.js:757-758, 2974-2975, 3015, 3043, 3077-3100`

三条路径的差异（复现要点）：

1. `logType==1` 不写 `numbersOfChannels` 之类的新字段，而是**复用同一份 schema**；
   TRACKSTAT 在 `logType==1` 下额外输出 `antenna = "SECONDARY"`，`logType==0` 下是 `"PRIMARY"`
   `[观察] logparsers.js:986` vs `:3011`。这是界面上「天线 1/2」切换的唯一依据。
2. `logType==1` 的 ITPSDDETECT 与 `logType==0` 的同 ID 分支代码完全重复（`:1146-1175` vs `:3043-3074`）。
3. 非 0/1 分支的返回值**没有 `tab` 之外的任何字段**，且会额外查
   `hexToStringConversion(str) == "Not enough resources in system"` 来置
   `jarvisInterface.OEM6MaxLogText[tab]` `[观察] logparsers.js:3093-3096`。

### 5.3 每个类型码的读法与宽度

| 类型码 | 读取 | 宽度 | 备注 |
|---|---|---|---|
| `UCHAR` | `getUint8` | 1 | |
| `HEX` | `getUint8` | 1 | **只是 1 字节**，与「十六进制串」无关；`extendedSolutionStatus` 用它读 bit 域 |
| `SHORT`（`ushortString`） | `getUint16(off,true)` | 2 | 名字里有 String 但返回整数 |
| `UINT_16` / `ULONG16` | `getUint16(off,true)` | 2 | 两个名字等价 |
| `ENUM` | `getUint32(off,true)` | 4 | 原始整数，查表另做 |
| `ULONG32` / `UINT_32` | `getUint32(off,true)` | 4 | |
| `INT_32` | `getInt32(off,true)` | 4 | 仅 `dcOffset` 与 WiFi `rssi` 用 |
| `FLOAT` | `getFloat32(off,true)` | 4 | IEEE754 |
| `DOUBLE` | `getFloat64(off,true)` | 8 | IEEE754 |
| `ULONG64` | `getUint64(off,true).toString(10)` | 8 | 返回**字符串**（`totalStorage/usedStorage`），避免精度丢失 |
| `STRING_4/8/12/16/18` | `getString(n,off).replace(/\0/g,'')` | n | 定长串，只去 `\0`，不 trim 空格 |
| `ustringvariable` | 见 §5.5 | 变长 | 返回 `{value,offset}` |

`[观察] logparsers.js:628-691`。**全部小端**（每个 `get*` 都传 `true`）。没有任何显式对齐填充：
字段偏移直接来自 schema，所以「对齐规则」实际上等同于「schema 里写死的补偿字节」
（例如 `BESTPOS` 中 `satellitesWithMultiFreqCount` 在 67、`extendedSolutionStatus` 在 69，
中间 68 字节被跳过 `[观察] logparsers.js:93`）。

### 5.4 比例因子

二进制日志本身用 IEEE float/double 传输物理量，**绝大多数字段 scaleFactor = 1**
（`parsers-fields.csv` 共 880 行，只有 4 行非 1）。真正需要换算的只有：

| 字段 | 原始 | 换算 | 算例 |
|---|---|---|---|
| 42 `idleTime` | `UINT8`，绝对偏移 12 | `v / 2` | `0x64=100` → 50 % |
| 963 `idleTime` | `UINT8`，绝对偏移 12 | `100 − v/2` | `v=60` → 70 %（表示空闲率，不是占用率） |
| 4098 `idleTime` | `FLOAT`，卡记录内偏移 28 | `100 − v` | `v=12` → 88 % |
| 1968/2063 `sample` | `UINT16` | `v/256 − 200` | `32768/256−200 = −72` dB |
| 1968/2063 `stepSize` | `FLOAT`（Hz） | `/1e6` 仅用于频率刻度 | `5e6` → 5 MHz 步进 |
| 1415/1417 `northOffset` 等 | `DOUBLE` | `.toFixed(2)` | 输出被转成**字符串** |

`[观察] logparsers.js:768, 1056, 3243, 1134-1136, 1127, 2942-2944`。
⚠ `idleTime` 两次出现在同一份 BESTPOS schema（`[uhex,12]`）与代码对偏移 12 的独立读取中，
说明 schema 的 offset 12 只是占位，真实语义由 `:767-769` 决定。

### 5.5 `ustringvariable`（变长串）与 4 字节对齐

```
从 abs = headerOffset + offset 起逐字节取字符，遇到 '\0' 停；
L = 已读字符数；rem = L % 4
  rem > 0 → 前进 (4 - rem)
  rem == 0 → 再前进 4（跳过 '\0' 再加 3 字节）
返回 {value, offset: 绝对下一字段起点}
```

`[观察] logparsers.js:664-690`。等价公式：**该字段占用 `ceil((L+1)/4)*4` 字节**。

算例（`fileList` 的 `fileName`，偏移 20）：

| 串 | L | 占用 | 下一字段起点（payload 内） |
|---|---|---|---|
| `"a.log"` | 5 | `ceil(6/4)*4 = 8` | 20 + 8 = 28 |
| `"abcd"` | 4 | `ceil(5/4)*4 = 8` | 28（**整字跳过**，不返回 24） |
| `"ab"` | 2 | `ceil(3/4)*4 = 4` | 24 |

⚠ 若整包内找不到 `'\0'`（`while` 走到 `dataLength`），函数**没有 return**（落出 switch）→ 返回
`undefined` → 调用处 `data.value` 抛 TypeError。`[观察] logparsers.js:667-690`。

`getNextOffesetBasedonLength(len)`（`logparsers.js:731-748`）是同一规则的独立实现，但只吃**串长度**，
不返回绝对值：`2101` 用它算 `errorMsg` 的起点 `12 + getNextOffesetBasedonLength(fileName.length)`。

## 6. 状态机与事件流

### 6.1 单包 → 视图

```
字节流 → genericparser 组帧(CRC≠0) → logBuffer(msgID,data,tab)
  ├─ GRIT/播放器分支：versionMessageId 先走 getMarketHwVersion + readReceiverProperties（只做一次）
  └─ 逐条 parseData → logData.time = getLogTimeStamp(data) → emitter('…') / genericView.updateView
```

`[观察] jarvisInterface.js:3529-3557`、`:3829-3855`。`connectionReady[tab]` 是「VERSION 已装配」的
门闩，装配完成后 VERSION 分支 `return`（回放除外）`[观察] :3853-3855`。

### 6.2 聚合型日志的状态机（4 条独立缓存）

`portData`、`fileListData`、`filesystemStatusData`、`ipServiceData` 是模块级对象，键为 `tab`：

```
收到一包 → push 到 cache[tab]
若 sequence == 0（末包）→ 返回 {data: cache[tab], tab}，并清空 cache[tab]
若 sequence != 0        → break（函数返回 undefined）
```

`[观察] logparsers.js:21-26, 1482-1510, 2272-2298, 2300-2326, 2328-2352`。
⚠ 返回 `undefined` 的路径会让调用方 `logData.time = …` 抛错，因此这四个消息的中间包在实时路径上
必然抛一次 TypeError 并被 `catch` 吞掉 `[推断] 由 :1510/:2298/:2326/:2352 的 break 与
jarvisInterface.js:3552 的赋值推得`。

### 6.3 positionModes 的两级状态机

- **配置态**：8 个 `isXxx(logData, tab)` 由 msgId 分派 `[观察] positionModes.js:42-86`；
  `checkBaseConfigured` 汇编 `RTK BASE / PSRDIFF BASE / NTRIP SERVER`（`:405-508`），
  `checkRoverConfigured` 汇编 `RTK ROVER / PSRDIFF ROVER / NTRIP CLIENT`（`:510-607`）。
- **激活态**：`portstatsMessageId` 用 `txChars` 增量判断是否在发差分数据 `[观察] :130-174, 618-644`。
- **对外口径**：`getOperatingMode` 只返回 `Transmit / Receive / Standalone` 三值（`:88-108`）。
- 前置条件：`featuresList.getPositionModesSupported(tab)` 必须已就绪（依赖 VERSION），否则
  `indexOf` 抛错 `[推断] :418, :516 直接对返回值取 indexOf`。

### 6.4 星座侧

`ConstellationHandler.satvisData` 以 `sequence == 0` 为「一轮 SATVIS2 收齐」的信号，把
`tabsatsdata[tab][system]` 整体交给 `handlingSatvis2Data`，再转 `Constellation`（普通）或
`gritConstellation`（GRIT tab）`[观察] constellationHandler.js:319-339`。
`generateData` 要求 SATVIS2 与 TRACKSTAT 都有数据才产出星座对象 `[观察] constellation.js:120-189`。

7. **INSPOSX 的 `INS_Status` 恒为 undefined** `[观察] logparsers.js:2127`：用
   `logResponseData.solutionStatus`（该消息没有这个字段）查表。真实意图是 `INS_Status`
   自身值，无法从代码确认。
8. **`satvis2.js` 与 `logparsers` 的 SATVIS2 双实现不一致** `[观察]`：前者要求
   `sync3 == 18`（`satvis2.js:33`）、字段名 `sv_id/elev/az`、块步进 40 但基址从 `h=28` 起；
   后者用 schema 偏移且 `satelliteId` 为 `ENUM`。两者的 `sequence` 语义也不同。哪一个是
   「权威」无法从代码判定。
9. **`43 RANGE` 与 30 余个目录内消息无解析器**：`messages-oem7.csv` 中标 `parsedByApp=false`
   的 562 条（如 43 RANGE、7 GPSEPHEM）说明这些日志只能被当「未知报文」丢弃。缺证据：是否有
   其它子系统（未在本次范围内）解析它们。
10. **`dummyJSON` 与 schema 字段名不完全对齐** `[观察]`：例如 `dummyJSON[42]` 含
    `satellitesUsed`，而 `bestposJSON` 的键是 `satellitesUsed`（一致），但 `dummyJSON[1246]`
    用 `baud` 而 `portConfig` 的 compRegister 里用 `bps`（`catalog-compRegister.json`）。
    这说明字段白名单与 schema 之间存在多处历史漂移，逐条对齐需要 UI 侧使用点，本次未逐个核对。
