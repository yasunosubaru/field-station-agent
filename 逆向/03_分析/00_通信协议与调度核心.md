> 覆盖：`controller\communication.js`、`controller\genericparser.js`、`controller\frameCommand.js`、
> `controller\crc.js`、`controller\pingpong.js`、`controller\connectionLostHandler.js`、

## 1. 职责

这五个文件构成整个套件的**唯一数据通道**：任何组件（Manage 的 status/config 瓦片、GRIT、Playback、
Convert 的实时预览）都不直接碰 socket，全部走 `controller` → `GenericParser` → `jarvisInterface.logBuffer`
→ `jarvisInterface.logProcess` → `emitter` 事件总线。 `[观察] 01_解包/app/controller/communication.js:707-719`、
`[观察] 01_解包/app/jarvisInterface.js:3822-3921`、`[观察] 01_解包/app/jarvisInterface.js:6373-6466`

四个协议面：

| 面 | 方向 | 实现位置 |
|---|---|---|
| NovAtel 二进制 SBF（长头 28 B / 短头 12 B） | 收 | `genericparser.js:13-192`、`:419-498` |
| NovAtel ASCII 全格式（`#…*crc`）/ 缩略 ASCII（`<…`）/ 端口前缀（`[…`） | 收 | `genericparser.js:252-274` |
| 命令构造：ASCII（带 CRC32）与二进制（`LOG`/`UNLOG`/`SENDHEX`） | 发 | `frameCommand.js:59-243`、`jarvisInterface.js:5320-5413` |
| 传输：TCP / UDP / 串口（含 9600 波特率 break 唤醒） / 回放文件 | 双向 | `communication.js:31-314` |

**消息目录必须在 `$(document).ready` 里手工装配**，否则 `MessageIdConstants.messageIds[rxGen]` 是

```js

MessageIdConstants.messageIds.OEM6    = M6MessageIdConstants.messageIds;  // 与 OEMSTAR 同一对象！
MessageIdConstants.messageIds.OEM7    = M7MessageIdConstants.messageIds;
```

### 5.2 CRC32 —— 已用手册向量验证

算法：反射多项式 `0xEDB88320`，**初值 0，末尾不做异或**（即 `CRC-32/ISO-HDLC` 去掉 init/final XOR）。 `[观察] crc.js:148-178`、`frameCommand.js:163-184`

用 `tools\crc_vector_test.js` 对手册给出的两个向量实测：

| 向量 | 输入 | 期望 | 结果 |
|---|---|---|---|
| ASCII | `BESTPOSA,COM1,0,78.0,FINESTEERING,1427,325298.000,00000000,6145,2748;…,06,0,03`（去掉 `#`，199 B） | `9c9a92bb` | **PASS** |
| 二进制 | 100 B 缓冲区（`AA 44 12 1C … 00 03`） | 字节序 `42 DC 4C 48`（u32 值 `0x484cdc42`） | **PASS** |

ASCII 日志写成 8 位小写十六进制；二进制日志写成 **小端** 4 字节。

### 5.3 ASCII 命令构造（`frameasciirequest`）

`[观察] frameCommand.js:186-243`，逐步：

1. `req.replace(/ +(?= )/g,'')` 压缩连续空格；空格 → 逗号 → 拆分。
2. 首字段若为 `log`/`unlog`（大小写不敏感）→ 统一大写。
3. 若 `reqarr[1]` 不是合法端口名（`NovatelPortNamesList`，含 `COM1_ALL`…`THISPORT_31` 等 400+ 项），
   在其前插入 `"thisport"`。
4. 拼装：
   ```
   "\r\n#" + 首字段 + "," + "THISPORT_30" + "," + "0,0,UNKNOWN,0,0,0,0,0;" + 其余字段(逗号连接)
   ```
5. CRC32 覆盖 **`\r\n#` 之后的全部字节**（即从首字段起），取 8 位小写 hex（不足左补 `0`），
   追加 `*<crc>\r\n`。

实例：`log bestposb ontime 1`
→
```
\r\n#LOG,THISPORT_30,0,0,UNKNOWN,0,0,0,0,0;thisport,bestposb,ontime,1*<crc8>\r\n
```
注意语义：头部第 3 字段固定 `THISPORT_30`，而 `LOG` 命令的**端口形参**是小写 `thisport`（无虚拟地址），
两者不是同一个东西。 `[推断] 依据手册 Table 2/3 头部字段定义 + LOG 命令语法`

### 5.6 成帧与半包处理

`processMessage`（`genericparser.js:13-192`）的总流程：

1. 先看是否有该 tab 的半包（`tempbuffermap`）。有则按类型合并：二进制 `mergePackets`，
   文本 `processText` 把新旧拼起来。 `[观察] :17-85`
2. 无半包则逐字节扫描，用 `getIndexes` 在剩余缓冲里同时找 6 种起点：
   `170`(0xAA 二进制)、`35`(`#` 全 ASCII)、`37`(`%` 短 ASCII)、`60`(`<` 缩略 ASCII)、
   `91`(`[` 端口前缀)、`36`(`$` NMEA)。取**最小索引**，即最早出现的那个。 `[观察] :194-228`
3. 二进制：读长度 → 若 `totalLen > 剩余` 就整段存半包并 `return`；否则切出整包，
   `crcindex = headerlen + messageLen` 取 CRC，**只判断 CRC 字段是否为 0，从不校验 CRC 值**
   （`if(exstcrc!=0)` → `logBuffer`），然后 `i = index + totalLen - 1` 继续扫。 `[观察] :108-168,139-141`
4. 文本：`end = indexOf(0x0A)`（ASCII/NMEA）或 `indexOf(0x5D)`（`[` 端口前缀，以 `]` 结尾）；
   找不到则整段存半包。找到后 `setTimeout(...,50)` 异步投递 `jarvisInterface.processDataForOtherFormats`。
   `[观察] :252-274`

两个**必须复现的怪癖**：

- 二进制分支的比较写成 `data[index+2] == '18'` / `== '19'`，靠 JS 的 `==` 做 `18 == '18'` 隐式转换；
  移植到强类型语言时必须显式写 `0x12` / `0x13`。 `[观察] :111,116,160`
- 短头分支只读 `getUint8(3)` 当长度，**不校验** `headerlen` 字段，也不校验 CRC。 `[观察] :123-141`

### 5.7 串口唤醒（break）与自动波特率

出厂接收机默认 9600，工具必须先「按住 break 三秒」把它拉回已知状态： `[观察] communication.js:573-621`

```
writeBreak: 以 setInterval(0) 连续发 0x55 01 01 00 40 00 05 9B，持续 250 ms
sendBreak: 250 ms → 停 1501 ms → 再来 250 ms → 停 300 ms → reEstablishSerial
reEstablishSerial: port.update({baudRate:9600})
                   → 1000 ms 后写 "command\n SERIALCONFIG THISPORT <baud> N 8 1 N ON\n
                                  INTERFACEMODE NOVATEL NOVATEL ON\n SAVECONFIG\n"
                   → 500 ms 后关端口 → 1000 ms 后以 tempactive=false 重连
```

自动波特率（`auto && buadrate == undefined`）用**递减**列表
`[460800, 230400, 115200, 57600, 38400, 19200, 9600, 4800, 2400]` 逐个尝试，打开成功即采用。
`[观察] communication.js:656-686`

### 5.8 接收机类型自动识别

四条互斥路径，全部在首包到达后 3–5 s 内决定：

| 场景 | 判据 | 结果 |
|---|---|---|
| UDP 网络 | 先发 `log ethstatusb ontime 1` 每 200 ms；收到回包即认为「可能是 GIII」，5 s 内无数据则退化为普通接收机 | `g3type=detect` → `GenericParser.autodetectGIII` |
| 以太网 GIII | 找 `AA CC 47 56` 魔数（0xAA 后跟 `CC 47 56`） | 发 `ICOMCONFIG ICOM1\n`，3 s 后置 `detected` |
| 串口 GIII | 先发 `SYSPROFILE\n`（100 ms 间隔），回包含 `INFO` 与 `SYSPROFILE` | `GIIIPortType='Maintenance'` |
| Longhorn/PIM222 | `pim222aRx` 且 3 s 内 `Edie.getreceivertype` 返回 `PIMTP`/`NMEA` | `setIsLongHorn(true)` + `getconfigfilelonghorn` |

`[观察] communication.js:61-155,197-310`、`genericparser.js:276-357`

## 6. 状态机与事件流

### 6.1 连接生命周期

```
openConnection
  ├─ TCP: connect → connectionStatus("connectionsuccess")   （注意：此时还不可用）
  ├─ UDP: bind + 200 ms 轮询 ethstatusb → 判定 GIII / 普通
  ├─ Serial/USB: 500 ms 后开端口 → open 事件 → connectionStatus("connectionsuccess")
  │             （active=true 时先跑 5.7 的 break 流程）
  └─ playback: playbackControl.play(file, tab)
        ↓
jarvisInterface.newConnection（建 tab、tabids、瓦片）
        ↓
controller.requestlog('log thisport_30 versionb once\n')   ← 由 newConnection 触发
        ↓
VERSIONB → logProcess → featuresList.readReceiverProperties → connectionReady[tab] = true
        ↓
requestInitialLogs → checkLogSpaceAndRequestData（等 loglistData 就绪，50 ms 轮询）
        ↓
compReqlogs(NovatelIdConstants.statusComponents) → 逐条 sendLogCommand("THISPORT_30")
        ↓
后续所有日志 → logBuffer → logProcess → smlogProcess → emitter.emit(...)
```

## 8. 复现清单

- `R1` 长头固定 28 字节，字段偏移与 §5.1 表完全一致；短头固定 12 字节。
- `R2` 二进制包只有在 `28+msgLen+4 <= 缓冲长度` 时才消费，否则整段入半包缓冲并等待下次数据。
- `R3` 二进制包只判断 **CRC 字段是否为 0**：为 0 丢弃，非 0 一律消费（**原实现从不校验 CRC 值**）。复现默认照抄，
  并另提供 `crcMode: 'validate'` 严格模式（`04_重实现/packages/protocol/src/framing.ts`）。
- `R4` 一个 TCP 段里可以含多个包；消费后 `i += totalLen - 1` 继续扫同一段，不得丢弃尾部残包。
- `R5` 短头与长头必须在同一条流里混合识别（`0x12` 与 `0x13`）。
- `R6` 文本行以 `\n` 结束（`#`/`%`/`$` 开头）或以 `]` 结束（`[` 开头）；未结束的行进半包缓冲，**不得**超时丢弃。
- `R7` `[` 端口前缀行必须原样透传给终端，不参与日志解析。
- `R8` 文本行投递到 UI 有 **50 ms** 延迟（原实现用 `setTimeout`），复现时保留以维持节流行为。
- `R9` CRC32 = 反射多项式 `0xEDB88320`、初值 0、无末尾异或；ASCII 写成 8 位小写 hex（左补 0），二进制写成小端 4 字节。
- `R10` 必须通过 §5.2 两个手册向量（`9c9a92bb` / `42 DC 4C 48`）。
- `R11` ASCII 命令必须按 §5.3 的 5 步改造，含「非端口名则插入 `thisport`」这一规则。
- `R12` ASCII 命令的 CRC 覆盖范围从首字段（`LOG`）开始，不含 `\r\n#`，不含 `*`。
- `R13` 命令必须以 `\r\n` 开头、以 `*<crc>\r\n` 结尾。
- `R14` 二进制 `LOG` 负载 32 字节，字段顺序与类型见 §5.4；`UNLOG` 8 字节。
- `R15` `trigger != ONTIME` 时 `period` 强制为 0。
- `R16` 字符串参数按 4 字节对齐补 `\0`；长度已是 4 的倍数时再补 4 个 `\0`（原实现如此）。
- `R17` 二进制命令的 `port address` 用 `THISPORT_30 = 222`，`messageType` 为 0（二进制）。
- `R18` 串口打开前延迟 500 ms；`active=true` 用 9600 打开并跑 break 流程。
- `R19` break 序列字节固定 `55 01 01 00 40 00 05 9B`，节奏 250 ms / 1501 ms / 250 ms / 300 ms。
- `R20` break 之后写 `SERIALCONFIG THISPORT <baud> N 8 1 N ON` / `INTERFACEMODE NOVATEL NOVATEL ON` / `SAVECONFIG`，再 500 ms 关端口、1000 ms 重连。
- `R21` 自动波特率按 §5.7 的**降序**列表尝试，成功即停。
- `R22` 端口枚举按 `manufacturer === 'novatel inc.'`（小写化后比较）分 USB 组，其余归串口组。
- `R23` Linux 下额外把 `/sys/class/tty/ttyS*` 里含 `pnp0` 的端口并入串口组。
- `R24` UDP 连接先发 `log ethstatusb ontime 1`，200 ms 一次；750 ms 内无任何回包则关闭并按 GIII 模式重连一次。
- `R25` GIII 以太网识别魔数为 `AA CC 47 56`；识别后发 `ICOMCONFIG ICOM1\n`，3 s 后强制置 `detected`。
- `R26` GIII 串口识别靠 `SYSPROFILE\n` 回包同时含 `INFO` 与 `SYSPROFILE`；识别后端口类型为 `Maintenance`。
- `R27` GIII 数据端口判别：`ICOMCONFIG` 回包中 port 与 `ICOMx` 一致且接口为 `ETHA` → `Data`，否则 `Monitor`；回包含 `ERROR:Command rejected` → `Data`。
- `R28` `connectionReady` 只有在收到 `VERSIONB` 且型号识别成功后置真；此前所有其它日志被丢弃。
- `R29` 连接成功事件在 socket `connect`/端口 `open` 时立即发出，**不等** `VERSIONB`。
- `R30` 心跳 5 s 一拍；`SENDHEX` 负载 6 字节；计数上限 2（Longhorn/GIII 为 4）；任何入站数据清零。
- `R31` 判死后必须：置 `connectionLostMap`、清 `tabids`、对所有共享同一 `tabids` 的 tab 调用 `connectionLostHandler.handleConnectionLost`、`closeConnection`。
- `R32` 时间戳 = `new Date('1980-01-06T00:00:00')` + `week*7*24` 小时 + `(ms - 18000)` 毫秒，即**硬编码 18 秒闰秒**。
- `R33` Idle Time 原始字节除以 2 才是百分比。
- `R34` 关闭连接前先发 `unlogall thisport_30 true\n`；GIII `Data` 端口发 `unlogall \n`。
- `R35` `UNLOG` 记账：`trigger == ONCE` 的日志不记入 `appLevelLogInfo`。
- `R36` 关闭时只 `UNLOG` 本 tab 独有的日志；被其它 opentab 共享的日志不得 `UNLOG`。
- `R37` `grit-tabs-N` 与 `tabs-N` 共享一个物理连接，关闭任一侧不得断开另一侧。
- `R38` 单条日志可同时投递给 SM 与 GRIT 两个视图，必须各自深拷贝。
- `R39` `logType != 0` 的包视作命令响应，走响应处理而非数据分发。
- `R40` `msgId == 128`（RANGE 的容器）需按 `getUint16(32)` 取内层 ID 再二次分派，且只处理 `configMessageIds` 白名单内的 ID。
- `R41` `configMessageIds` 恰好 28 个（见 `jarvisInterface.js:30`），新增/删除必须同步。
- `R42` `MessageIdConstants.messageIds` 的 5 个世代键必须按 index.html:1182-1198 装配，且 OEMSTAR/OEM6、OEM7/SMART2 共享同一对象。
- `R43` `MessageIdTweaks` 的覆盖只对**已存在**的 msgId 生效（`if (msgID in …)`）。
- `R44` 收到 `#VERSIONA` 且第 2 字段含 `_29` 时，把它记为 `connectedPortName`。
- `R45` 所有解析异常必须被捕获且不中断数据流（原实现用 `try{…}catch(e){console.log(e)}` 包住整条分派链）。

## 9. 未解之处

1. `SENDHEX` 心跳的真实负载 —— **`[已解 2026-10-30，OEM729 真机]`**
   手册 §2.163：`SENDHEX [port] length data`，`data` 必须是**十六进制串**。真机实测（COM7 = USB3）：

   ```
   发  SENDHEX USB3 6 143Ab5900D0A
   收  [USB3] <OK [USB3] 14 3A B5 90 0D 0A        ← 六字节原样到达目标端口
   发  SENDHEX USB3 6 Sendhx                       ← 等价于 pingpong 里 "Sendhxdt" 的前 6 字节
   收  [USB3] <ERROR:Invalid Message. Field = 2    ← 按 data 字段被拒
   ```

   结论：`pingpong.js:12-27` 的 `message:["Sendhxdt",'string']` + `length:6` **是无效负载**，
   接收机拒绝，这颗心跳从未起过作用——这也解释了为什么断链判定只能靠"任何入站数据清零"
   （`communication.js:55`）而不是心跳回执。重实现默认仍镜像该负载，但暴露
   `heartbeat.payload` 供按手册发送真实六字节（见 `00A §8 D10`）。
2. `_28` / `_29` 虚拟端口语义 —— **`[已解 2026-10-30，OEM729 真机]`**
   真机 `LOGLIST` 正在使用这两组：

   ```
   USB1_29 RAWEPHEMB ONNEW / BESTPOSB ONTIME 1 / RANGEB ONTIME 0.05 /
           PORTSTATSB ONTIME 10 / RXSTATUSB ONCHANGED / HWMONITORB ONTIME 10
   USB2_29 同上
   ```

   与同时抓下的 USB1/USB2 原始字节逐条对得上（`00_来源/samples/raw/com8-*.bin`）。手册 Table 5
   的端口标识是「基址 + 虚拟序号」（`USB1` 基址 1440、`USB3` 1952），Table 6 另给
   `USB1_ALL` / `FILE_ALL` 之类别名；**28 / 29 不是手册里的特殊值**，是套件自选的虚拟组号
   （一组给数据口、一组给文件/抽稀），接收机接受 `<物理口>_<n>` 写法。

3. `port == 61/93/125/189` 分支里 `recordToBufferOnTabBasis` 的去重条件依赖
   `shortHeaderDupLogs[tab][name+'B']` 的单调时间戳比较，若接收机时间回跳会永久丢日志。是否为有意设计未知。 `[未知]`
4. `crc.CalculateCrcResponse` 是半成品（`return 0` 且内部错误循环），无法确定作者原意；
   所有实际 CRC 校验走的是 `genericparser` 里 `getUint32(crcindex)` 的 `!= 0` 判断。 `[未知]`
5. `GenericParser.processMessage` 的 `navigator.userAgent` IE 分支（`:87-97`）在 Electron 下永不执行，
   视为死代码，但保留了 `getIndexes` 的数组版本语义，复现时可省略。 `[推断]`
