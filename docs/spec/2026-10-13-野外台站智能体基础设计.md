## 0. 这份文档解决什么

申报书已经写死了要做什么（五类智能体、七步技术路线、考核指标）。缺的是承载它的骨架：
仓库怎么放、地基是什么、旧代码整合到什么程度、什么算做完。

**本版相对第 1 版的顺序调整**：先建骨架、再整合旧代码、再立框架，**真实数据接入排在最后**。
理由：数据可以后补，但"从三份历史资产里取什么、为什么取、什么坚决不取"必须在写第一行业务
代码之前定死。否则每个模块都会顺手把老代码复制进来，到结题时边界就糊了。

本设计只覆盖**基础**（仓库 + 整合 + 框架 + 评测底座），不含五类智能体的逐一实现。

| 不搬的东西 | 规模 | 理由 |
|---|---|---|
| `inversion.py` + `_algo_compare.py` + `mapping.py` | ~1,700 行 | TEC 反演专用，台站管理用不上 |

这个比例本身要写进结题材料 —— 它同时证明了"没有重复劳动"和"没有把别人的成果充自己的"。

### 1.5 两个必须记住的反面案例

- **hflink 的论文不在仓库里**，一个按相对路径查找论文的脚本因此在每个克隆上失败，
  连带整个发布门禁在全新克隆上必然失败。教训：本项目所有跨文档引用的产物
  **要么入库，要么脚本能优雅降级**，不留"必须联网补数据才能验证"的部分。
- **GNSS 项目 `test_qc_wiring` 三项静默跳过**，selftest 停在 3/5 ——
  因为"不接 QC 就会有 105 个负 TEC"这个核心论点的唯一证据被跳过了，而 unittest
  不会因为跳过而报错。教训：**复制代码必须连测试一起复制**，且 selftest 必须是 5/5。

## 2. 仓库与目录

新建独立仓库 `field-station-agent`，位于工作区第四个独立文件夹
``（以 git rev-parse --show-toplevel 为准）``。

**不并入**另外三个已结项项目，互不引用、不共库，各提交各的路径。
仓库原为私有；后经负责人决定**脱敏后公开**（真实姓名、学号、本机路径已全部移除）。
本设计文档本身不含未公开方案细节，公开不构成泄密。

```
野外台站智能体/
├── README.md              # 一分钟上手 + 现状（由 sync_code_counts 机维护）
├── CLAUDE.md              # 工作区规矩
├── PROVENANCE.md          # 每个搬运件的：源仓库/源路径/commit/日期/改动行
├── src/fieldstation/
│   ├── agents/            # 智能体 —— 地基本身
│   │   ├── runtime/       #   角色定义、工具注册、消息路由、上下文管理
│   │   ├── tools/         #   工具注册包装（schema/校验/错误语义/返回归一）
│   │   ├── memory/        #   共享黑板 + 检索知识库
│   │   ├── trace/         #   决策留痕
│   │   └── providers/     #   模型适配层（provider 抽象，配置外置）
│   ├── ingest/            # ← §1.1 的 obsfile/obs_registry/schema 落此
│   ├── rules/             # ← §1.1 的 qc/constants 落此（工具实现，非本项目成果）
│   ├── store/             # ← §1.1 的 product 落此
│   └── cli.py             # 统一入口
├── harness/
│   ├── replay.py          # 回放式评测器 ← 借鉴 selftest/config/batch 的模式
│   ├── selftest.py        # exit 0 才算通过
│   └── REPRODUCE.md
├── tools/                 # ← §1.2 三个移植件落此
│   ├── audit_claims.py  sync_code_counts.py  make_cli_figures.py
├── tests/                 # ← §1.1 的 7 个测试文件落此（6+1，见 §1.1 附注）
├── data/ logs/ figures/ config/ docs/
```

**搬运件的归属规则**：物理上落在 `rules/` 与 `tests/`，但在 `agents/tools/` 下
**只放注册包装**（schema、入参校验、错误语义、返回值归一化）。
agent 只能看到注册后的工具，看不到 `rules/` 的内部实现。
每个搬运件在 `PROVENANCE.md` 里必须写清身份转换：
"此文件在原项目中是独立算法模块，在本项目中是智能体可调用工具背后的实现"，
并改名为 `rules/` 下的对应模块，避免看起来像本项目原创的算法。

## 3. 阶段顺序：先骨架，再整合，再框架，最后数据

### 3.1 M0 阶段（2026-10 — 11）：四步，不碰真实数据

| 步 | 内容 | 验收 |
|---|---|---|
| M0-1 骨架 | 目录、`CLAUDE.md`、`PROVENANCE.md` 模板、`git init`、首次提交 | 目录与本文档 §2 一致 |
| M0-2 整合 | 搬 10 个文件 + 7 个测试（原计划 6 个，实测补 t7_support）；移植 3 个工具；建 `rules/` 身份转换 | `tests/` 全绿且**跳过数为 0**；`tools/audit_claims.py` 能跑通并输出报告（内容随结题材料增长） |
| M0-3 框架 | `agents/` 五个模块的**接口先定死**，用 stub + 一个 fake provider 实现 | 空链路能跑通：有输入 → 有 trace → 有输出 |
| M0-4 评测底座 | `replay.py` + 合成 fixture + SHA256 复现性断言 | 同输入两次跑 SHA256 相同 |

M0 全部不依赖真实数据，也不含任何真实 LLM 调用（用 fake provider）。
目的是让框架本身先能被测，而不是先被业务代码撑变形。

### 3.2 评测集怎么办（先不碰数据的关键）

智能体项目没有评测集就没有基线。解法：用 §1.1 搬来的 `synthetic.py` 生成
**合成 fixture**（注入已知噪声/周跳/缺测/粗差，注入规则与种子入库），
先跑通回归基线；真实台站数据留到 M2。

`test_pipeline.py` 里的**合成数据隔离**概念必须继承：合成产物写进独立目录，
不与真实数据混放，防止合成数据被误当真实数据交付 ——
GNSS 项目的 figures 目录就有"真实数据图 + 合成图隔离区"的先例。

### 3.3 M3 阶段（2027-01 — 02）：第一个真 Agent

```
观测数据 → ingest 适配器 → rules 工具（周跳/量级/连续性守卫）
                            ↑
                    Agent 调用工具
                            ↓
              归因结论 + 处置建议 + 置信度
                            ↓
                   trace 落盘 → 回放式评测
```

LLM 从 M3 才真正进入链路。三条硬指标：

1. **可复现** —— 固定数据集 + 固定 seed + 固定模型，同一输入两次跑结论一致
2. **可追溯** —— 每条结论都能挂回它调用过的工具输出，不允许无据结论
3. **有判据** —— 在标注样本集上跑出归因准确率，写进 README 与结题报告

第 3 条是本项目区别于"调了个 API"的地方：它是**有评测基线**的智能体系统。

> 注：第 1 版把 M0 的第一条纵切定为"不碰 LLM 的数据管道"，理由是怕无地基盖二层。
> 该顾虑改由 §3.1 的**回放式评测底座**解决 —— 框架先能被测，
> 而不是靠推迟 LLM 来避免被测。

## 4. 智能体运行时（框架要求）

`agents/runtime/` 必须提供：

| 能力 | 说明 | 验收 |
|---|---|---|
| 角色定义 | 职责、可用工具、输出契约，声明式配置 | 新增 agent 只加配置，不改代码 |
| 工具注册 | schema、输入输出约束、错误语义集中注册 | agent 只能调用已注册工具 |
| 消息路由 | agent 间通信走消息总线，不共享隐藏状态 | 消息全量落 trace |
| 上下文管理 | 共享黑板（台站/告警/工单上下文）读写受控 | 并发访问语义明确 |
| 决策留痕 | 模型调用与工具调用的输入/输出/耗时/token 全量落盘 | 任一结论可回放到工具输出 |
| provider 抽象 | `chat(messages, tools) -> response`，配置全外置 | 换模型不改编代码 |

**五类 Agent 不并行开工。** 运行时先做扎实，再用它实例化；顺序反了就是五份各写各的烂代码。

## 5. 模型通道：双轨

用户已确认「两者都要"。

- **回归基线走本地模型**：Ollama / vLLM 起一个 7B 量化模型
  （默认 `qwen2.5:7b-instruct`，中文归因优于同尺寸英文模型，单机可跑）。
  断网、额度耗尽时 `harness/replay.py` 仍能完整跑通 —— 这是评测基线成立的**前提**。
- **正式数字走 API**：DeepSeek / 通义等学生免费额度通道，出可写进结题报告的指标。
- **M0 阶段两者都不用**：用 fake provider，先测框架本身。

**必须在接 API 前验证**：固定 seed + `temperature=0` 下 API 是否真能复现。
若不能，正式指标改用多次运行的分布（如 5 次归因准确率的均值与极差）并如实说明 ——
不能声称可复现而实际不可复现。

**经费风险**：1000 元没有 API 预算。若届时额度不可得，以本地模型结果作为结题指标，
并如实标注模型规模。

## 6. Definition of Done

一条 issue 算完成，需同时满足：

1. 代码在 `main`，走 PR 合入，不直接 push
2. `python -m unittest discover -s tests` 全绿（**跳过数必须为 0**）
3. `python harness/selftest.py` 退出码 0
4. `logs/` 下有实测输出，且每个对外数字可由 `tools/audit_claims.py` 回源核对
5. agent 相关改动：`harness/replay.py` 重跑得分不劣于改动前，且分数本身可复现
6. README「现状」一节由 `sync_code_counts.py` 同步更新（不手写）

第 2 条的"跳过数为 0"直接来自 GNSS 项目 `test_qc_wiring` 的教训。
第 4 条来自 `audit_claims.py` 的 47 项回源核对纪律。

## 8. 明确不做的事（YAGNI）

- M0 阶段不接真实台站数据、不做看板、不调真实 LLM
- 不做微服务拆分，不引入消息队列中间件（进程内消息总线足够）
- 不做多租户、权限体系（三人团队，用仓库权限即可）
- 不引入向量数据库（知识库初期用 SQLite + 全文检索）
- 不重造 RINEX 解析与质控判据（已搬）
- 不搬任何一次性排障脚本（§1.4）

## 9. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 搬运件与原项目混淆 | 结题说不清哪部分是一年成果 | PROVENANCE.md + 改名 + 独立提交历史 |
| 搬运时漏拷测试 | selftest 静默降级，核心论点无证据 | DoD 第 2 条"跳过数为 0" |
| 框架被业务代码撑变形 | 返工 | M0-3 先定死接口并用 stub 测 |
| API 不可复现或额度中断 | 结题交不出指标 | 本地模型回归通道兜底（§5） |
| 智能体结论不可信 | 运维场景代价高 | 规则裁决、LLM 只做归因；高风险动作人工审批 |
| 范围膨胀（智能体 + 配套 + 看板） | 五类 Agent 一个都交付不了 | §6 DoD + M3 只做一个 Agent |
| 1000 元无硬件 | 台站接入做不深 | 真实接入列为可裁剪项，公开数据优先 |
