## 1. 先验的四件事（`tools/dbos_probe.py`，4/4 通过）

计划书要求"不做完不许往下走"。四条全过，所以按原方案做。实测记录：

| # | 验什么 | 怎么验 | 结果 |
|---|---|---|---|
| 1 | 工作流能起、能出结果 | `DBOS(...).launch()` + `@workflow` + `start_workflow` + `get_result` | `add(3,4) -> 10`，step 只调 1 次 |
| 2 | 步骤只执行一次 | 跑到第 2 步中间 `os._exit(9)` 强杀，重启 | 已完成那步**没重跑**，续跑结果 6 |
| 3 | 睡觉不占进程 | 进 `sleep` 后 kill，重启 | 睡之前那步没重跑，续跑结果 3；进程真的死过 |
| 4 | 能收发信号 | `send` / `recv` | `recv` 收到 `approved`，工作流被唤醒 |

复跑：`python tools/dbos_probe.py`（退出码 0 = 全过）。

### 1.1 「步骤只执行一次」到底是什么意思（这条一开始写错了）

**准确的说法是两条，不是一条：**

| 情形 | 会不会重跑 | 为什么 |
|---|---|---|
| 崩溃时**已记完**的步骤 | **不会** | DBOS 有它的完成记录，续跑直接跳过 |
| 崩溃时**正在执行**的那一步 | **会重跑一次** | 它还没被记为完成，DBOS 只能从头再来 |

实测证据（把每步的 `begin/end` 都写进文件）：

```
杀之前：begin:1  end:1  begin:2      ← 第 1 步完成，第 2 步在飞
续跑后：00 个新的 begin:1，一个 begin:2、end:2，然后第三步
        总计 begin 4 个、end 3 个 —— 多出来的那个 begin 就是在飞的第 2 步
```

**所以验收断言不能写成"每步只跑一次"。** 第一版就是这么写的，结果一会儿红一会
儿绿：红了是因为第 2 步重跑了一次，绿是因为三步跑得太快、杀的时候已经全跑完了
（那是**空转**，什么都没验到）。

现在的断言是三条：

1. 杀之前**已完成**的那一步，整场只出现一次 `begin`（这才是"不重跑"的判据）；
2. 杀的时候**在飞**的那一步，允许出现第二次 `begin`，但不超过两次；
3. **反空转**：必须证明杀的时候确实是"前一步完成、下一步在飞"，否则用例不算通过。

第 3 条最容易被省掉，但它才是让这个用例真正有效的那条。

**这条对写代码的影响**：带副作用的 action 必须能承受"最多重跑一次"。
所以设备动作一定要带幂等键（`idempotency_key`），写文件要能覆盖而不是追加。
「重放不重复调工具」这个说法只在"崩溃瞬间不在执行"时成立，不能当默认前提。

### 1.2 同一个坑在 LangGraph 闸门上又出现一次

Bot-3 的 `interrupt()` 有完全相同的形状：闸门节点在恢复时**从函数开头重跑**，
所以 `interrupt()` 之前的副作用会执行两遍。两处结论合起来是全项目的一条纪律：

> **带副作用的动作必须能承受"最多执行两次"。**

细节见 `docs/operations/graph-interrupt.md` §2。

### 1.2 另外三个 API 事实

| 事实 | 影响 |
|---|---|
| `start_workflow()` **立刻返回**（实测 0.03s），工作流在后台线程跑 | 调用方不需要 `threading` 就能拿到句柄；但**不能**靠"调用返回"判断已完成 |
| 工作流在 `sleep` 期间状态是 `PENDING` | 「卡在闸门等人」可以直接从 `get_workflow_status()` 观测，不用自建状态位 |
| `DBOS.launch()` 会**自动恢复**本应用版本下所有未完成工作流 | 崩溃续跑不用写代码；但**测试之间必须换库或换应用名**，否则上一个用例的半截工作流会跑进下一个 |

最后一条踩过：探针一开始各用例共用一个目录，第 3 项启动时把第 2 项没跑完的
工作流也复活了。

### 1.3 两个工程坑

| 坑 | 症状 | 处理 |
|---|---|---|
| DBOS 启动日志很多 | 用 `subprocess.PIPE` 接子进程 stderr，日志**塞满管道**导致子进程卡死、父进程等到超时，现场看起来像"程序挂了" | 子进程 stderr 重定向到文件 |
| 子进程输出里有中文 | 父进程用 `text=True` 时按系统 GBK 解码，报 `UnicodeDecodeError` | 显式 `encoding="utf-8"` |

## 2. 编排层怎么摆

### 2.1 两个库，分开

```
<业务库所在目录>/
  botd.sqlite        ← 我们自己的九张表（业务镜像）
  dbos.sqlite        ← DBOS 系统表（执行真相）
```

**为什么要分**：DBOS 的系统库里有几十张自己的表，还会自己跑 schema 迁移
（本机实测建库时跑了 120+ 个 migration）。混进业务库会让两套迁移互相干扰，
而且 `PRAGMA user_version` 只有一格，两边都会用它。

### 2.2 一个任务 = 一个工作流，id 就是 task_id

用 `SetWorkflowID(task_id)`，于是：

- **同一 `task_id` 重复投递只跑一次** —— 这就是 Bot-1 验收第 2 条，
  不需要在应用层再做去重。
- DBOS 的工作流 id 与 `task.task_id` 一一对应，两本账用同一个键对，不用维护映射表。

### 2.3 哪些动作必须包成 `@step`

判据只有一个：**重放一次会出问题吗？**

| 动作 | 包不包 | 理由 |
|---|---|---|
| 调工具 / 写文件 / 发消息 / 写业务库 | **必须包** | 重放会重复扣 token、重复写、重复通知 |
| 读记忆、算数、格式化字符串 | 不包 | 重放无害，包了只是多一次 DBOS 写 |

**这条判据的代价**：漏包一个写动作，崩溃续跑时它就会再执行一次。所以编排层里
凡是带副作用的调用一律走 `self._step_*` 包装，不直接裸调。

### 2.4 闸门

```
写动作 → DBOS.sleep(...) → 人批（intervention 表） → DBOS.send(...) → 醒来
```

用 `sleep` 而不是自建轮询，因为第 3 项已经验过"睡的时候进程可以死"。
醒来靠 `send`/`recv`（第 4 项）。

## 3. 与业务表的关系

`task` / `step` 是**业务镜像**，DBOS 系统表是**执行真相**。两边同步规则：

| 时机 | 写哪边 |
|---|---|
| 任务入队 | 业务表 `task`（`pending`）；DBOS 工作流还没起 |
| 工作流启动 | DBOS 自动记；业务表 `task.status = 'running'` |
| 每步完成 | DBOS 记 step；业务表 `step` 回写 |
| 闸门挂起 | 业务表 `task.status = 'waiting_approval'`（**must not be `pending`**，否则会被队列重新领走） |
| 终态 | 两边都写；不一致时**以 DBOS 为准**，业务表跟着改 |

`run_link` 的写入按契约 §4 七步时序，其中第 3 步（thread）与第 4 步（agent）
由编排层在进场时写，`provider` 分别是 `langgraph` / `letta`。
