### 怎么改

**第 1 处：版本号（第 27 行）**

`SCHEMA_VERSION` 从 `1` 改成 `2`。

**第 2 处：新增 `_MIGRATE_V2`（插在第 192 行 `_SCHEMA_V1` 结束的 `"""` 之后、第 195 行 `class BotStore` 之前）**

这一段内容分四块，**顺序不能换**：

| 块 | 内容 | 依据 |
|---|---|---|
| ① 建 `thread` 表 | 10 列 + 1 个索引 | 契约 §2.2 |
| ② 建 `agent` 表 | 12 列 + 1 个索引 | 契约 §2.3 |
| ③ 建 `work_order` 表 | 15 列 + 2 个索引 | 契约 §2.4 |
| ④ 给 `run_link` 加 `kind` 列 + 按 provider 回填 + 加复合索引 | 1 句 ALTER + 3 句 UPDATE + 1 句 CREATE INDEX | 契约 §2.5 + §5 迁移表 |

**三个必须照抄的细节**（少一个就会在后续出问题）：

1. **`thread.status` 的 CHECK** 必须是 `('open','idle','closed','broken')` —— 后面续跑逻辑靠这四个状态判断
2. **`work_order.priority` 的 CHECK** 必须是 `('P0','P1','P2','P3')` —— 排序依赖它
3. **回填 `kind` 的三条 UPDATE** 必须按 provider 区分：
   `langgraph`/`dbos` → `thread`；`letta` → `agent`；`ledger` → `work_order`
   **写错的话，旧数据会指向错的表，查询全部返回 NULL**
4. **`run_link` 的 `bot_id` 列不删** —— 契约要求移到 `detail.bot_id`，但删列会破坏旧数据。保留，在文档里标 deprecated

**第 3 处：`migrate()`（第 255 行起）**

加一个 `if version < 2:` 分支，内容是 `executescript(_MIGRATE_V2)` + `PRAGMA user_version = 2`。

**关键**：必须靠 `PRAGMA user_version` 控制只跑一次，**不能**靠「先检查列存不存在」。
理由是 SQLite 的 `ALTER TABLE ADD COLUMN` 重复执行会抛 `duplicate column name: kind`。

**第 4 处：状态常量（第 32 行附近）**

新增六个常量：`THREAD_STATUSES` / `AGENT_KINDS` / `AGENT_STATUSES` / `WO_PRIORITIES` / `WO_RISKS` / `WO_STATUSES` / `LINK_KINDS`。
值与 DDL 里的 CHECK 完全一致。

**第 5 处：三组读写原语**

每组三个函数（建 / 读 / 改状态），照 `create_task` / `get_task` 的写法保持一致。

三个注意点：

| 点 | 具体 |
|---|---|
| JSON 字段 | `agent.allowed_tools` 和 `work_order.evidence_call_ids` 存的时候 `json.dumps`，读的时候 `json.loads` |
| 高风险工单 | `risk=high` 的工单要进 `done`，必须先有 `approved_by`，否则抛 `E_PRECOND` |
| `run_link` 追加型 | 解除关联是 `UPDATE status='unlinked'`，**不是 DELETE** |

**第 6 处：`link()` / `unlink()`**

`link()` 要处理重复：同一个 `(provider, external_id)` 再 link 一次，是更新而不是插两行。
靠 `ON CONFLICT(provider, external_id) DO UPDATE`。

### 改成什么样

跑完这六处改动后：

- 新建一个库，`PRAGMA user_version` 返回 **2**
- `sqlite_master` 里有 **9 张表**：原来的 6 张 + `thread` / `agent` / `work_order`
- `PRAGMA table_info(run_link)` 里有 **10 列**：原来的 9 列 + `kind`
- 原有的 18 项队列测试**仍然全绿**（这次改动不该破坏任何既有行为）

### 怎么改

**第 1 处：`store.py` 的 DDL 改成 v3 迁移，不改 `_SCHEMA_V1`**

为什么不用改 `_SCHEMA_V1`：因为已有数据库已经按 v1 建好了。
改 `_SCHEMA_V1` 只影响新建库，已有库不会变。所以必须走迁移。

`_MIGRATE_V3` 包含三条：

| 句 | 作用 |
|---|---|
| `ALTER TABLE task RENAME COLUMN id TO task_id` | 改主键 |
| `ALTER TABLE task RENAME COLUMN parent_id TO parent_task_id` | 改父引用列 |
| `DROP INDEX` + `CREATE INDEX` | **重建父索引**（改名后原索引失效） |

**第三条很容易漏。** 漏了不会报错，只会让「按父任务查子任务」悄悄变慢。

**第 2 处：`_task_dict()` 不用动**

我核实过它是通用实现（`_row_dict(row)` + 把 `payload`/`result` 解 JSON），
**不写死列名**，改名后自动跟着变。**别在这里浪费时间。**

**第 3 处：逐文件改调用点**

判断标准只有一个：**这个 `id` 是不是从 `get_task()` / `list_tasks()` 拿的？**
- 是 → 改成 `task_id`
- 不是（`step["id"]` / `bot["id"]` / `memory["id"]`）→ **不动**

**不要全局替换。** 78 处里混着四种不同的 `id`。

**第 4 处：`tests/test_run_link_contract.py` 里的 `t.id AS task_id` 改回契约原文 `t.task_id`**

### 改成什么样

- 全量测试：**`Ran 1647 tests, OK (skipped=0)`**
- **数字必须还是 1647，skip 必须还是 0**

| 如果变了 | 说明什么 |

| 变成 1646 | 有个测试文件整个挂了 |

| 红了 | 逐条看报错，判断那个 `id` 属于哪张表 |

### 怎么改

验四件事，每件都要真跑：

| 验什么 | 为什么关键 | 不成立意味着 |
|---|---|---|
| 工作流能起、能出结果 | 最基本能力 | DBOS 不能用，方案要换 |
| 步骤只执行一次 | 重放时不重复调工具 | 会重复扣 token、重复写文件 |

**任何一条不过 → 停下来报告，不要硬改。**

**第 2 步：建编排层骨架（`orchestrator.py`）**

三个部分：

| 部分 | 内容 |
|---|---|
| `configure()` | 建 DBOS 实例。数据库落在 `store.path.parent / "dbos.sqlite"`，**和业务库分开但同目录** |
| `bot_task_run(task_id)` | 一个任务 = 一个工作流。**声明**，先空壳 |
| 子任务入队 | 走现有 `TaskQueue.enqueue`，**不替换它** |

**第 3 步：把调用链接起来（按契约 §4 的 7 步时序）**

```
① 记忆召回（Letta，只在开头）
② 图执行（LangGraph，推理真相）
③ 派子任务（走 TaskQueue）
④ 写动作 → 挂起 → 睡觉 → 人批 → 醒来
⑤ 记经验（Letta，只在结尾）
⑥ 写台账（work_order + run_link）
```

**关键判断：哪些动作必须包成「步骤」？**

标准是：**这个动作重放一次会出问题吗？**
- 会（写文件、调工具、发消息、写库）→ **必须包**
- 不会（读内存、算数、格式化字符串）→ 不用包

**第 4 步：换 cron**

`cron.py` 现在是自建调度（235 行）。换成 DBOS 自带的定时。
换完后原来的 15 项 cron 测试要跟着改。

**第 5 步：`workflow` / `step` 表的镜像**

DBOS 有自己的系统表。我们的 `task` / `step` 表是**业务镜像**。
两边要同步：DBOS 工作流状态变了，业务表也要更新。

### 改成什么样

三条验收，逐条真验：

| 验什么 | 怎么验 | 期望 |

| 杀进程重启继续 | 起 3 步流程，跑到第 2 步**强杀进程**（`Stop-Process`，不是 Ctrl+C），重启 | 从第 2 步继续，第 1 步不重跑 |

| 睡觉不占进程 | 工作流睡 60 秒，期间看内存 | 内存回到基线 |

## Bot-8 · 干预在步骤边界生效

**前置**：Bot-1（编排层的循环）、Bot-2（队列）。

### 涉及文件

| 要读的 | 内容 |
|---|---|
| `src/fieldstation/botd/supervisor.py` 第 345–406 行 | `_drive()` 的完整循环。**第 360 行是 `queue.lease`，干预检查要插在它前面** |
| `src/fieldstation/botd/interaction.py`（399 行） | 干预的四种 `kind`：`pause` / `resume` / `retry` / `takeover`；`effective_boundary()` 的语义 |
| `src/fieldstation/botd/store.py` | `list_interventions()` / `resolve_intervention()` 的签名 |

| 要改的 | 改什么 |
|---|---|
| `src/fieldstation/botd/supervisor.py` | `_drive()` 里加边界检查；新增两个私有方法 |
| `tests/test_botd_intervention_boundary.py`（新建） | 六条验收 |

### 怎么改

**第 1 处：`_drive()` 的循环开头（第 360 行 `queue.lease` 之前）**

加一段：读待处理干预 → 按 kind 决定是否继续。

四种 kind 的四种反应：

| kind | 反应 |
|---|---|
| `pause` | 不再领新步；当前步跑完就停；父任务置 `waiting_operator` |
| `resume` | 清掉标记，继续领 |
| `retry` | 那一步重跑，`attempts + 1` |
| `takeover` | 那一步不交给执行器，置 `waiting_operator` 等人工结论 |

**第 2 处：新增 `_consume_intervention(task_id)`**

读一条 pending 干预 → 标记为已消费 → 返回 kind。

**关键：必须标记为已消费**，否则同一个暂停指令会被反复读到，永远停不下来。

**第 3 处：新增 `_set_waiting(task_id, status)`**

把父任务状态改成「等人操作」。

**第 4 处：位置纪律（这是本条最容易被做错的地方）**

**必须在「领步之前」读，在「执行之后」读。**

不能在工具执行到一半时插进去 —— 那样日志里会留一条 `tool.call` 没有对应的 `tool.result`，
事后没人能说清那个工具到底跑完没有。

### 改成什么样

六条验收，逐条都要有测试：

| # | 验收项 | 易错点 |
|---|---|---|
| 1 | 暂停后下一步不被领走 | **不是立刻抛异常**，是「不再领」 |
| 2 | 正在跑的那一步**跑完**才停 | 需要慢执行器（故意睡 1 秒）才能观察到 |
| 3 | 继续后能接上 | — |

### 怎么改

`dist/` 里那个 904 MB 的 exe，是 **.NET WPF + WebView2** 壳。
构建时那个提交里 `botd/` `data/` `graph/` `runtimes/` `shell/electron/` **全都不存在**。
