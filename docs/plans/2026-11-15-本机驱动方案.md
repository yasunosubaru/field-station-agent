# 本机驱动方案（2026-11-15，v3 三层驱动修订）

- 结论先说：**不引入第二个操作系统。** 套件还是本机已装的那一份（2.11.0.1586），
  靠「几何三层固化 + 前置清理 + 三级定位 + 原生对话框 UIA」把 8 条流程推到
  `auto` 或明确的 `assisted`。
- 沙盒（sbx / Windows Sandbox / Hyper-V）**不用**。理由见 §1，结论见 §12。
- 每一条都标「现状来自哪个文件」+「本机是否验过」。**没验过的会明确写「未验」**。

> **v1 → v2**：v1 的第 0 层有三条来自网上、未在本机验证的假设。实测后
> 两个探针落地：`tools/probe_cdp_viewport.py`、`tools/probe_cdp_click.py`。
>
> **v2 → v3（本次）**：v2 把 `tscon` / 注册表 / 虚拟显示器判成「不需要」，那是**错的**——
> 当时只看本机会话（console 直连），忽略了真正跑 RPA 的是远程机（必然 RDP 会话）。
> 实测本机两次查询之间主屏自己从虚拟屏换成物理屏，证明**物理屏不是常量**。
> 现改为 **第 0 层三层缺一不可**：虚拟显示屏 → 会话保活 → CDP 视口。
> 实施顺序随之拆成三批，几何地基层排最前。

---

## 1. 为什么本机是主线，沙盒不用

| 判据 | 本机 | 沙盒 |
|---|---|---|
| 套件 | 已装、已解包、已逆向对齐 | 要重装，Linux 版还要重新做字段对照 |
| 硬件 | 本机 COM/USB 直通 | 要 USB passthrough 或改 TCP |
| GPU | RTX 5080 + Intel 双显卡 | `sbx` 只有 swiftshader（实测） |
| 脏状态 | 有，但可用 `restore_home` 治住（§4） | 每次重装，天然干净但慢 |
| Windows Sandbox | — | **不可用**：`wsb` CLI / `WindowsSandbox.exe` / Appx 全不存在 |

**沙盒换掉的是宿主，不是通道。** 8 条流程的难点（原生对话框、弹窗残留、几何漂移）
在 Linux 上一样存在，还得把 UIA 重写成 AT-SPI。所以在唯一一套已验证的宿主上把通道补完。

Windows Sandbox 另外还有两个硬伤：`wsb exec` **拿不到 stdout**（微软文档明说
"no support for process I/O"），错误信息得靠文件回传；而且每次销毁套件要重装。

## 2. 五层结构

```
第 0 层  几何固化（驱动的地基，三层缺一不可）
         ├─ 第一层  虚拟显示屏      → 物理分辨率是常量
         ├─ 第二层  会话保活        → 图形上下文还在绘制
         │            tscon /dest:console + SuppressWhenMinimized + SetThreadExecutionState
         └─ 第三层  CDP 视口钉死    → 页面布局基准是常量

第 1 层  前置清理（每条流程开头）
         └─ restore_home：关残留弹窗 → 结束残留对话框 → 回首页 → 验证

第 2 层  定位（三级，按稳定性排序）
         ├─ CDP 语义（文字/选择器）—— 首选
         ├─ 坐标（钉视口 + 命中签名）—— 语义抓不到时
         └─ UIA（原生 Windows 对话框）—— CDP 够不着时

第 3 层  闸门与证据（已具备）
         ├─ human_gate（不可逆前停）
         └─ artifacts（截图 + job.json + audit.jsonl + sha256）

第 4 层  失败分类与恢复（已具备，八类）
         └─ 每类一个明确的「下一步谁动」
```

> **第 0 层为什么是三层**：CDP 只能改"页面认为视口多大"，改不了
> "Windows 有没有在画"。RDP 断开时会话变 `Disc`，窗口停止绘制、截屏报"句柄无效"——
> 这时 CDP 一点用都没有。所以物理分辨率、绘制上下文、页面视口是三个独立条件，
> 少一个坐标就失去意义。

## 3. 第 0 层：几何固化（驱动的地基，三层缺一不可）

### 3.1 设计原则：虚拟显示器**随软件启动，无条件启用**

这不是"某种场景需要时才开"的增强项，而是**产品的一部分**：

| 原则 | 含义 |
|---|---|
| **随包启动** | 外壳拉起 Node 服务之后、启动套件之前，先确保虚拟显示器在位并切到目标模式 |
| **无条件** | 不管本机还是远端、有没有物理屏、是不是 RDP 会话 —— **一律用虚拟屏**，不判断“要不要” |
| **不需要人看** | 原版套件跑在虚拟屏上，物理屏显示什么与它无关；人可以继续用本机做别的事 |
| **失败即报** | 虚拟屏不在 / 切不过去 → 流程报 `environment` 停下，绝不退到物理屏继续点 |

**为什么是“无条件”而不是“按需”**：一旦允许“这次用物理屏、下次用虚拟屏”，坐标基准就有两个，
而两者的分辨率、DPI、Packery 布局全不同。**判断本身就会引入漂移。** 只留一个基准最省事。

### 3.2 为什么必须让坐标有意义

驱动原版的第一步不是"点哪里"，而是**让坐标有意义**。这需要三个独立条件同时成立：

| 条件 | 谁失效它 | 谁保证它 | 影响哪条点击路径 |
|---|---|---|---|
| 物理分辨率是常量 | 插拔外接屏、RDP 连入/断开、息屏、笔记本合盖、远程机无物理屏 | **虚拟显示屏（无条件启用）** | 只影响 UIA 截图/物理坐标；CDP 路径无关 |
| 图形上下文在绘制 | RDP 断开（会话变 `Disc`）、窗口最小化 | **`tscon` + `SuppressWhenMinimized`** | 两条路径都受影响（Windows 不画，页面也不合成） |
| 页面布局基准是常量 | 窗口大小变化、DPI 不同、Packery 重排 | **CDP `setDeviceMetricsOverride`** | 只影响 CDP 路径 |

#### 3.2.1 先纠正一条被读错的证据（v4 修正）

v3 曾用下面这条"实测"当"物理屏不是常量"的论据：

| 时刻 | 主屏 | 分辨率 |
|---|---|---|
| 之前 | `DISPLAY19` = GameViewer **虚拟屏** | 2560×1600 |
| 现在 | `DISPLAY1` = **Intel 物理内屏** | 1707×1067 |

**这条论据站不住。** `1707×1067` 是 DPI 假象，不是屏幕变了：

```
2560 / 1.4997 = 1707      1600 / 1.4997 = 1067
```

本机 `LogPixels = 144`（150%）。`GetSystemMetrics(SM_CXSCREEN)` 对 **DPI-unaware 进程**
返回虚拟化后的像素，对 DPI-aware 进程返回物理像素。`tools/probe_dpi_screen.py` 实测：

| 视角 | 读数 |
|---|---|
| DPI-unaware `GetSystemMetrics` | 1707×1067 |
| `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` 后 | **2560×1600** |
| 驱动 `EnumDisplaySettingsW("\\.\DISPLAY1")` | **2560×1600@240** |

比值 1.4997，与 150% 一致。物理屏**一直是** 2560×1600@240，从来没变成 1707×1067。

**但这不推翻"虚拟屏无条件启用"的结论**，只推翻它的旧论据。真正让物理屏变成变量的
是这些事件（都不需要 DPI 解释）：

- RDP 连入/断开改会话分辨率；笔记本合盖 `DISPLAY1` 直接消失；
- `tools/probe_display_paths.py` 实测：`QDC_ONLY_ACTIVE_PATHS` 只有 **1 条**通路，
  `QDC_ALL_PATHS` 有 28 个 source 但 27 个 `NOT connected`；
- 远程机 `DESKTOP-9POIV0O` 无物理屏 —— 那时没有 `DISPLAY1` 可退。

**顺带纠正另一条**（v3 也写错了）：CDP 路径的**点击不依赖物理屏**。
`click_engine` 走 `Input.dispatchMouseEvent`，用视口坐标，与 DPI、窗口大小都无关
（`probe_cdp_click.py` 已实测：800×600 窗口里点 (1860,990) 仍然 HIT）。
依赖物理屏的具体是：

| 操作 | 依赖物理屏 | 原因 |
|---|---|---|
| CDP 点击 / 读 DOM | **不依赖** | 视口坐标，与窗口和 DPI 无关 |
| CDP 截图 | **不依赖** | `Page.captureScreenshot` 走合成器，不是屏幕抓取 |
| UIA 点击 | 不依赖 | 走 `InvokePattern`，不是坐标 |
| **UIA 截图** | **依赖** | `Graphics.CopyFromScreen` 抓的是真实屏幕 |

所以虚拟屏的第一层对「CDP 全链路」是**冗余的保险**，对「UIA 截图」才是必需品。
保留它仍然正确——它让 UIA 与 CDP 两条路共享一个基准；但要如实写明哪条路真需要它。

### 3.3 第一层：虚拟显示屏 —— 固定物理分辨率（**随软件启动**）

| 项 | 内容 |
|---|---|
| 作用 | 给 Windows 一块**分辨率不变**的绘制目标，与物理屏、RDP 会话完全脱钩 |
| 启用时机 | **外壳启动时**：Node 服务就绪后、拉起套件前。不是可选步骤 |
| 目标模式 | 1920×1080@60（与 CDP 视口一致，免掉一层缩放换算） |
| 真正需要的路径 | **UIA 截图**（`Graphics.CopyFromScreen`）。CDP 点击/截图不依赖物理屏，见 §3.2.1 |
| 缺了怎么办 | 装微软签名的 IDD 驱动（`IddSampleDriver` / Virtual Display Driver）。**打包时随包附带**，首次启动安装 |
| 交付物 | `tools/setup_display.ps1` —— 枚举适配器 → 选中虚拟屏 → `ChangeDisplaySettingsEx` 切目标模式 → 读回校验 → 失败明确报错 |

**启动顺序**（写进外壳，不靠人记得跑）：

```
外壳启动
  → 解压 payload
  → 起 Node 服务（READY <port>）
  → setup_display.ps1         ← 虚拟屏就位，切 1920x1080@60，读回校验
  → keep-desktop.ps1          ← 注册表 + 计划任务（会话保活）
  → 起原版套件（suite_launcher，注入 CDP 端口）
  → 开窗指向 Node 服务
```

> **注意**：`EnumDisplaySettings(NULL, …)` 返回 0 种模式（本机实测）。必须显式传设备名
> `\\.\DISPLAYnn`。判断"当前用哪块屏"也不能看序号，要看 `StateFlags` 的
> `0x1`（ATTACHED_TO_DESKTOP）与 `0x4`（PRIMARY_DEVICE）。

#### 3.3.1 本机实测：虚拟屏存在，但**都没有接桌面**（v4 新增，如实记录）

`tools/setup_display.ps1 -List` 与 `tools/probe_display_paths.py`（只读）实测：

| 适配器 | 控制器 | 状态 | `EnumDisplaySettings` 模式数 |
|---|---|---|---|
| `\\.\DISPLAY1` | Intel(R) Graphics | **attached, primary** | **102**（含 1920×1080@60） |
| `\\.\DISPLAY5-8` | NVIDIA RTX 5080 | 未接桌面 | **0** |
| `\\.\DISPLAY9-18` | `OrayIddDriver Device` ×10 | 未接桌面 | **0** |
| `\\.\DISPLAY19-28` | `GameViewer Virtual Display Adapter` ×10 | 未接桌面 | **0** |

`QueryDisplayConfig(QDC_ONLY_ACTIVE_PATHS)` 只有 **1 条**通路（`DISPLAY1`）；
`QDC_ALL_PATHS` 列出 28 个 source，其中 27 个标 `NOT connected`。

**这意味着 `setup_display.ps1` 会在退出码 2 停下** —— 不是脚本写错了，而是本机
这些虚拟屏驱动**只在厂商软件主动挂接时才创建 source/target 通路**，没有通路时
`ChangeDisplaySettingsEx` 无从施力。`OrayIddDriver` 与 `GameViewer` 都属于
"由厂商客户端按需开启"的那一类，不是自启常驻的独立虚拟显示器。

**因此有两条可选路线，必须二选一（当前未定）：**

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 随包带独立 IDD 驱动** | 打包附带 `IddSampleDriver`（微软签名样例）/ Virtual Display Driver，首次启动装驱动并 `SetDisplayConfig` 建通路 | 自包含，不依赖厂商软件，无外部客户端 | 需要管理员装驱动；驱动签名与版本要跟着 Windows 更新走 |
| **B. 调用厂商客户端挂接** | 启动时调 `GameViewer`/`OrayIddDriver` 的挂接接口（当前**未找到公开入口**） | 不装新驱动 | 未验证可行；依赖第三方软件在位与版本 |

**当前状态：A 未实现，B 未找到入口。** 计划书不假装这一层已经能工作。

**踩到的两个坑（已绕过，别人也可能撞）**：

1. **`WindowsUserModeDriver10.0` 平台工具集不存在** —— VS 18 用 `v145`，而 WDK
   `10.0.26100.0` 只集成了 VS 2022（`v143`）。`msbuild` 直接报 MSB8020。
   绕过方式：`tools/idd/build-cl.bat` 直接调 `cl.exe`，手工给头文件与导入库路径。
2. **正确路径是 `umdf\2.35` 而不是 `umdf\1.11`** —— `1.11` 是 UMDF **1.x** 时代的
   `wudfddi.h` 体系，`IddSampleDriver` 用的是 UMDF **2.x**。链接需要
   `Lib\wdf\umdf\x64\2.35\WdfDriverStubUm.lib` + `Lib\<ver>\um\x64\iddcx\1.6\iddcxstub.lib`。

**还没做的（诚实标注）**：

| 待办 | 阻塞原因 |
|---|---|
| 装驱动并验证「能枚举到 1920×1080@60」 | 需要管理员提权，且要真装机 |
| 签驱动 | 需证书；本机 `SecureBoot=0` 可以装测试签名，但交付机不一定 |
| 把 `.sys` + `.inf` + 签名放进 payload | 依赖上两条 |
| `setup_display.ps1` 自动发现并选用这块屏 | 依赖装驱动完成 |

> **交付形态提醒**：IDD 驱动没法「双击就能用」。用户首次启动一定会遇到一次管理员
> 授权（`pnputil /add-driver ... /install`）。这不是实现缺陷，是 Windows 的硬约束。

**降级路径（`-PreferPhysical`，已实现，但**不是**替代方案）**：`setup_display.ps1 -PreferPhysical`
可以让流程物理屏跑通。它能用的边界必须写清，否则会被误当成「第一层可以不做」：

| 场景 | 物理屏做基准 | 为什么 |
|---|---|---|
| 同一台机、同一块屏、桌面常亮 | 可用 | 分辨率不变，视口钉死，坐标可复现 |
| 换一台机器（不同分辨率/DPI/多显示器） | **会漂** | 布局基准是视口，但 `ensure_display` 校验的是物理模式；物理模式随机器变，等于每台机器一套坐标 |
| 插拔外接屏 / 笔记本合盖 | **会漂** | `DISPLAY1` 可能消失或变成别的设备 |
| RDP 连入 / 断开 | **会漂或直接失败** | 会话分辨率变化；断开后 Windows 不绘制 |
| 远程机无物理屏 | **不可用** | 没有 `DISPLAY1` 可退 |

**所以物理屏不是等价替代，是「单机单屏」限定下的临时可用。** 产品要跑在任意机器上，
这条就不能当答案 —— 这正是选 B（随包带独立 IDD 驱动）的理由。

> **v5 修正**：本条此前写成「CDP 全链路正常，只有 UIA 截图会抓到物理屏内容」，
> 那是过度断言。真正被实测的只有「同一台机上视口钉死后坐标可复现」；
> 「换机器不漂」没有被测过，且按上表推理**不成立**。

#### 3.3.3 v6（2026-11-17）：**第一层已打通并实测成功**

一句话结论：**驱动装好之后，还差一个 `SetDisplayConfig` 调用；而这个调用必须「少给参数」。**

```
SetDisplayConfig(0, NULL, 0, NULL, SDC_TOPOLOGY_EXTEND | SDC_APPLY)   // rc = 0
```

实测结果（本机，`tools/ensure_virtual_display.py` 输出）：

```
monitor[0]  pos=(0,0)     size=2560x1600   ← Intel 物理屏（PRIMARY）
monitor[1]  pos=(2560,0)  size=1920x1080   ← VDD 虚拟屏
SM_CMONITORS = 2        SM_CXVIRTUALSCREEN = 4480 x 1600
\\.\DISPLAY231  state_flags=0x08000001  ATTACHED   mode 1920x1080@60
```

`0x08000001` 里的 `0x1` 就是 `DISPLAY_DEVICE_ATTACHED_TO_DESKTOP` —— **真的接上了桌面**，
不是「存在但未激活」。持续观察后仍在，不掉线。

**用的哪家驱动**：`VirtualDrivers/Virtual-Display-Driver`（VDD）官方签名版
`Signed-Driver-v24.12.24-x64.zip`，`MttVDD.dll` + `mttvdd.cat` 签名均为 `Valid`
（`CN=SignPath Foundation` / 颁发者 GlobalSign）。装法见 `tools/install-vdd.ps1`。

**目录里同时留着我编译的微软样例驱动**（`tools/idd/`），它的历史价值是两个坑的实测记录，
但**产品线走 VDD**：VDD 自带 `vdd_settings.xml`（`<count>1</count>` + `1920x1080@60`）
和官方驱动重启机制，样例没有。

##### 为什么之前 7 次全失败 —— 根因是「多加了 flag」

逐项用 `SDC_VALIDATE`（只校验、不应用、屏幕不闪）验过：

| flags | `SDC_VALIDATE` |
|---|---|
| `TOPOLOGY_EXTEND` | **0** ✅ |
| `TOPOLOGY_EXTEND \| VIRTUAL_MODE_AWARE` | **0** ✅ |
| `TOPOLOGY_EXTEND \| ALLOW_CHANGES` | 87 |
| `TOPOLOGY_EXTEND \| VIRTUAL_MODE_AWARE \| ALLOW_CHANGES` | 87 |
| `TOPOLOGY_EXTEND \| NO_OPTIMIZATION` | 87 |
| `TOPOLOGY_EXTEND \| SAVE_TO_DATABASE` | 87 |
| 任何带 `USE_SUPPLIED_DISPLAY_CONFIG` 的组合 | 87 |

**拓扑类 flag 一旦叠加修饰符就整体失效。** 之前每次都顺手加
`ALLOW_CHANGES` / `VIRTUAL_MODE_AWARE`（"以防系统改我的配置"），看起来更完备，
实际直接让调用返回 `ERROR_INVALID_PARAMETER`。

##### 顺带抓到的两个自己的 bug（写下来避免重犯）

| bug | 后果 | 正确值 |
|---|---|---|
| `DISPLAYCONFIG_MODE_INFO_TYPE_SOURCE` 写成 2 | 把 TARGET 模式当 SOURCE 绑给 path，一律 `rc=87` | **SOURCE = 1、TARGET = 2** |
| 用 `QDC_DATABASE_CURRENT` 查配置 | `GetDisplayConfigBufferSizes` 返回 0，但 `QueryDisplayConfig` 返回 **87**；只看前者会误判成功 | 改用 `QDC_ONLY_ACTIVE_PATHS` |

##### 已知限制：布局**不持久化**

| 检查项 | 实测 |
|---|---|
| `GraphicsDrivers\Configuration` | **0 个子项** |
| `GraphicsDrivers\Connectivity` | **0 个子项** |
| `QDC_DATABASE_CURRENT` 内容 | 2 条 `WinDisc`（已断开），且 `QueryDisplayConfig` 实际 `rc=87` |
| `EXTEND \| APPLY \| SAVE_TO_DATABASE` | `rc=87`（该修饰符不能与拓扑类组合） |

**后果：重启后双屏需要重新执行一次 `tools/ensure_virtual_display.py`。**

这**不影响**产品设计 —— §3.6 本来就要求「每次启动都跑一次几何固化」，而不是指望
Windows 记住。`ensure_virtual_display.py` 已是幂等的：已接上只报告，未接上就 `EXTEND|APPLY`。
反而把「布局不可持久化」变成无关紧要：启动链每次都重建一遍。

##### 这条路的硬约束（交付时必须告诉用户）

IDD 驱动没法「双击就能用」。装机时需要**一次管理员授权**（`pnputil /add-driver`），
这是 Windows 的硬约束，任何 IDD 都绕不过。VDD 官方安装器（`.exe`）实测**未签名**，
所以我们只取里面的签名驱动文件，不走安装器 —— 见 `tools/install-vdd.ps1` 头部注释。

### 3.4 第二层：会话保活 —— 保证图形上下文还在

| 项 | 作用 | 本机状态 | 需要管理员 |
|---|---|---|---|
| `tscon <id> /dest:console` | 把**断开的 RDP 会话**交还 console，让窗口继续绘制 | 工具可用（v10.0.26100.8457，签名 Valid）；当前 `console=1 Active`、**无 Disc 会话可作用** → **未实测生效** | 改别的会话需要 |
| `RemoteDesktop_SuppressWhenMinimized = 2`（DWord） | RDP 窗口最小化后仍继续绘制 | **已验证 HKCU 可写**（写入 DWord=2 → 读回 → 用 `.reg` 恢复未设置）；**未启用** | **不需要** |
| `SetThreadExecutionState(ES_CONTINUOUS\|ES_SYSTEM_REQUIRED\|ES_DISPLAY_REQUIRED)` | 防息屏/睡眠打断长时间 RPA | 未做 | 不需要 |

**为什么必须有这层**：RDP 断开时 Windows 把会话标成 `Disc`，之后
`GetForegroundWindow()` 返回 0、`Graphics.CopyFromScreen` 报"句柄无效"、
Electron 不再重绘。**CDP 改不了这件事** —— 它只能改"页面认为视口多大"，
改不了"Windows 有没有在画"。

**触发时机**：`tscon` 只在「RDP 连入 → 断开 → 会话变 `Disc`」之后有意义。
交付物 `tools/keep-desktop.ps1`（纯 ASCII），由计划任务在会话断开事件
（`TerminalServices-LocalSessionManager/Operational` **事件 24**）触发；
`SuppressWhenMinimized` 与 `SetThreadExecutionState` 在流程开始时设一次即可。

> 安全提醒：`tscon ... /dest:console` 会让控制台会话**保持解锁**。
> 必须接受「能看到物理屏的人就能操作已登录会话」这一前提。
> 不接受就只能用无人值守的物理隔离机，或退回沙盒路线。

### 3.5 第三层：CDP 视口钉死 —— 页面布局基准（**已实测通过**）

`Emulation.setDeviceMetricsOverride` 只改页面视口，不动物理屏。

| 1280×800 | 1280×800 ✓ | 1.0 ✓ | 未变 ✓ | (100,200) 精确 ✓ |
| 2560×1600 | 2560×1600 ✓ | 1.0 ✓ | 未变 ✓ | (100,200) 精确 ✓ |

|---|---|---|
| `inside` | (70,40) | HIT |
| `edge` | (760,530) | HIT |

### 3.8 关于 DPI（一个被推翻的假设）

## 5. 第 2 层：三级定位 —— **语义失败必须能退到真鼠标**

这是整个方案里最容易被忽略、却直接决定“点得动点不动”的一节。

### 5.1 问题的根源：现在点的不是“真鼠标”

`cdp_driver.click()` 对普通 locator 走的是 `_click_js`，最后一行是 **`el.click()`**。
那是 **JS 合成事件**，不是真鼠标点击：

| 它不做 | 后果 |
|---|---|
| 不发 `pointerdown` / `mousedown` | 靠 `pointerdown` 判定的控件**根本不进处理器** |
| 不触发 `:hover` | 悬停才展开的菜单点不到 |
| 不更新焦点 | 输入框拿不到焦点，后续 `type` 落到别人身上 |
| 不检查遮挡 | 被半透明遮罩盖住的卡片，`el.click()` 照样"成功"，但用户点不到 |

原版套件里这三类目标会因此**静默失败**：点了一下，没反应，也没报错。

### 5.2 三级升级链（已实现并实测）

`ClickEngine.click_escalating()` + `CdpDriver.escalating_click()`：

| 级 | 定位方式 | 点击方式 | 覆盖 |
|---|---|---|---|
| **1** `semantic-realmouse` | `collect()` 目标池 + `pick()` | **`Input.dispatchMouseEvent` 真鼠标** | 有文字 / `cursor:pointer` 的元素 |
| **2** `coord-signature` | CSS 选择器 → 中心点 | **真鼠标** + `elementFromPoint` 命中签名校验 | 语义池过滤掉的元素（无文字图标块、`cursor:default` 的 div） |
| **3** 抛错 | — | — | 带上每一级的失败原因，**绝不静默** |

**关键澄清：第 2 级不是“退回到更差的手段”。** 它换的是**定位方式**（CSS 直取，
不受语义池的文字/role/光标过滤），点击仍然是真鼠标，而且**多一道命中签名校验**——
比第 1 级更严格。

`ClickEngine._hover/_press/_release` 的真实实现：

```python
_hover  → Input.dispatchMouseEvent {type: "mouseMoved", x, y, button: "none"} + 等 80ms
_press  → Input.dispatchMouseEvent {type: "mousePressed", x, y, button: "left", clickCount: 1}
_release→ 先 sleep(0.04)（真鼠标按下/抬起间隔 30~80ms，太短会被框架判成抖动）+ mouseReleased
```

走浏览器自己的命中测试：**点不到会表现为断言失败，而不是假成功。**

### 5.3 已实测（`tools/probe_escalation.py` + `tools/probe_driver_escalation.py`）

| # | 断言 | 结果 |
|---|---|---|
| 1 | 语义路径（`_click_js`）点不到无文字 div | **PASS** |
| 2 | 语义路径能点到普通按钮（对照组） | **PASS** |
| 3 | `record_coords` 能记录该 div | **PASS** |
| 4 | 坐标 + 真鼠标 点中该 div | **PASS** |
| 5 | 点击记录带命中签名 | **PASS** |
| 6 | 坐标故意偏 200px → `elementFromPoint` 报“坐标漂移” | **PASS** |
| 7 | `click_escalating` 自动升级到 `coord-signature` 并点中 | **PASS** |
| 8 | `CdpDriver` 暴露 `escalating_click` | **PASS** |
| 9 | 普通 `click` 对该 div 报错（不是假成功） | **PASS** |
| 10 | `_locator_to_css` 只把“能确定唯一元素”的写法翻成 CSS | **PASS** |

11 项全过。第 6 条是坐标模式能被信任的理由：**签名不符就报错，不硬点。**

### 5.4 怎么在流程里用

```yaml
- id: click_apply
  kind: gui
  actions:
    - action: click
      locator: "target:Apply"
      css: "#apply-btn"        # ← 可选；写了就走三级升级
```

- **只写 `locator`**：保持原行为（第 1 级），不改变既有 8 条流程的语义；
- **同时写 `css`**：走三级升级，`audit.jsonl` 里会记 `escalation` 是 `semantic-realmouse`
  还是 `coord-signature`，事后能看出这一下到底靠什么点中的；
- `_locator_to_css` 只翻**能确定唯一元素**的写法（`#id`、`.cls`、`[attr]`、`css:...`、
  纯 id 名）；纯文字（`"Normal Button"`）翻不出 CSS 时返回 `None`，
  **不会硬猜坐标**——按文字模糊匹配出来的“第 N 个候选”不适合当坐标基准。

### 5.5 驱动不支持升级时

`runner._click_escalating()` 做能力探测：驱动有 `escalating_click` 就用，
否则退化为普通 `click()` 并记 `escalation: "driver-click"`。
所以 UIA / assisted / scripted 驱动**行为完全不变**。

### 13.4 必须修的三处

**① `tools/` 的裸导入 → 改成按路径加载**

```python
# 现在（cdp_driver.py:284）—— 只在 tools/ 进了 sys.path 时成立
from click_engine import ClickEngine

# 改成
import importlib.util as _iu
from pathlib import Path as _P
_spec = _iu.spec_from_file_location("_fsa_click_engine",
                                    _P(__file__).with_name("click_engine.py"))
_mod = _iu.module_from_spec(_spec)
_spec.loader.exec_module(_mod)
ClickEngine = _mod.ClickEngine
```

NAS 范围内受影响的是 **6 处**：`cdp_driver.py`（1）、`rpa_calibrate.py`（2）、
`rpa_fixture.py`（2）、两个新探针（2）。
`agent_server.py`（3）与 `check_agent_specs.py`（1）属于 Agent 侧，不在 NAS 范围。

**② `build_payload.py` 补齐漏收的脚本**

| 文件 | 现在 | 必须收 |
|---|---|---|
| `tools/click_engine.py` | **未收** | ✓（`cdp_driver` 依赖它） |
| `tools/rpa_fixture.py` | **未收** | ✓（`restore_home` 在这里） |
| `tools/rpa_calibrate.py` | 未收 | ✓（selector 漂移时要用） |
| `tools/rpa_lint.py` | 未收 | ✓（`--check` 门禁用） |

**③ 打包链改成「标准库 only」的 Python，并去掉重复**

现在同一套 Python 环境被**两条打包链各放一遍**，产物里出现两套 `site-packages`：

| 位置 | 大小 | 形态 | 谁放的 |
|---|---|---|---|
| `app/dist/py-runtime/` | 1489 MB | venv（`Scripts\python.exe` + `Lib\site-packages` 1478 MB） | `tools/build-release-v5.ps1` |
| `resources/app/payload/runtime/python/` | 1287 MB | embed（`python.exe` + `Lib\site-packages` 1281 MB） | `tools/build_payload.py` |

实测两处都是 **346 个包、清单完全相同**（`Compare-Object` 双向为空），
只是 `pandas`（72 vs 36.7 MB）、`pyarrow`（88.7 vs 83.9 MB）等版本不同 ——
说明是**不同时间分别装的两次**，不是同一次拷贝。

**混合版真正需要的 Python 只有标准库。** 所以：

| 动作 | 结果 |

### 13.7 验收（新增）

1. `python tools/probe_stdonly.py` → exit 0（模块级零第三方）；
2. `python tools/probe_packaged_imports.py` → exit 0（`tools/` 内零裸导入）；
3. **干净机验收**：一台没装 Python、没装 Node 的 Windows，双击 exe，
   `/api/health` 返回 `ok:true`，8 条 workflow 的 `describe` 全部可读；
4. 断网验收：拔网线后核心功能仍可用（只有联网类流程会报 `environment`）；
5. **体积验收**：① ≈ 166 MB + ② 1562 MB，合计 ≤ 1750 MB；
   **`py-runtime` 只出现一次**，且 `site-packages` 里没有 §13.5 列的 15 个大包；
6. **重复打包验收**：解包后 `py-runtime` 只出现一次（现在是两处）。
