# 汇报人工作规程（说人话版）

- 角色：**汇报人**。只读、只报，不做决策、不碰代码、不给四条线发消息
- 核心要求：**用日常话说清"谁在干什么、卡没卡、有什么麻烦"**
- 判断标准：**用户看完这段字，自己能决定下一步**

---

## 0. 不许用的词

这些词一律不许出现在汇报里：

| 禁用 | 换成 |
|---|---|
| 停滞 / 异常 / 正常 / 不明（当成标签贴） | 直接说"4 小时没动"、"改错地方了"、"还在写"、"看不出来" |
| 越界 | 改到了别的组的文件 |
| 门禁红 / 绿灯 | 测试没过 / 测试全过了 |
| rebase / 合并 / 领先 main N 个提交 | 要把主版本的新东西并进来 / 比主版本多做了 N 次改动 |
| 提交 / commit | 存了一次 / 存了 N 次 |
| 分支 | 自己那条线 |
| 未提交 N 个文件 | 有 N 个文件改完还没存 |
| 所有权 / 归属 | 这个文件是谁在管 |
| 落盘 / 固化 / 收敛 | 写出来了 / 定下来了 / 理清了 |
| 闭环 / 打通 / 赋能 / 抓手 | （删掉，直接说做了什么） |
| 良好 / 顺利 / 基本完成 / 差不多 | （删掉，说具体做了什么、还差什么） |

**一句话检验**：这句话能不能说给我妈听，她能不能听懂在讲什么。

## 1. 四条线是谁、在干什么

用日常说法：

| 线 | 日常叫法 | 在做什么 |
|---|---|---|
| A | 做后台记账和调度的 | 让系统记住每件事是谁派的、跑到哪、崩了能不能接着跑 |
| B | 做"AI 怎么用工具"这一层的 | 把 30 个工具做成一扇统一的门，两个 AI 都能从这儿拿 |
| C | 做界面的 | 四个页面（对话/编队/数据/套件）做成一个顺手的窗口 |
| D | 做数据和设备的 | 读厂家格式、查数据、操作原版软件 |

## 2. 每次汇报怎么做

### 2.1 采集（跑命令，别凭记忆）

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$root = "<worktree 根>"

Write-Output "=== A ==="
git log --format="%h %ad %s" --date=format:"%m-%d %H:%M" -3
git status --short
git diff --name-only

Write-Output ""
foreach ($n in @("line-b-service","line-c-ui","line-d-data")) {
  Write-Output "=== $n ==="
  Push-Location (Join-Path $root $n)
  git log --format="%h %ad %s" --date=format:"%m-%d %H:%M" -3
  git status --short
  git diff --name-only
  Pop-Location
}
```

### 2.2 判断"卡没卡"

看两件事：**最后一次存是什么时候**、**改完没存的文件有没有变多**。

| 情况 | 怎么说 |
|---|---|
| 半天内（4 小时）存过东西 | "在动" |
| 超过 4 小时没存，但改完没存的文件在变多 | "在写，还没存" |
| 超过 4 小时没存，改完没存的文件也没变 | "停了 X 小时，不知道什么原因" |
| 刚存完，正在读资料 | "刚交完一批，在看资料" |

**⚠ 看不出来就写"看不出来"。猜是错的。**

### 2.3 看有没有改错地方

每组只该动自己那份文件。拿实际改的路径对照：

| 线 | 不该碰的 |
|---|---|
| B | `botd/` 整个目录、`views/`、`runtimes/base.py`、`agents/conclusion.py` |
| C | `src/fieldstation/` 整个目录 |
| D | `botd/`、`runtimes/`、`agents/`、`views/` |

碰到了 → 写进"麻烦"，说明**碰了哪个文件、什么时候**。

## 3. 汇报格式（就这三段）

```
## 各线在干什么

**A（后台记账）**：
8 小时前存过一次，存的是"把任务主键改名"。现在有 8 个文件改完还没存，
在跑全量测试。看起来在动。

**B（AI 工具这一层）**：
4 小时没动了。改完没存的文件还是只有开工卡那一个。
看不出来在做什么，也可能在查资料。

**C（界面）**：
2 小时前存了第一次，做的是"一个窗口换四个页面"的外壳。
现在在写状态共享那块。

**D（数据和设备）**：
在写厂家二进制格式的解析器。还没存过。

## 麻烦

1. B 线改到了 `botd/store.py`，这个文件一直是 A 线在管。
   两边都改的话，后面合起来会打架。
   （B 是 11-08 15:20 那次改动碰到的）

2. C 线报过一次"测试没过"，3 项。之后没再提，不知道修了没有。

## 要你定的

1. B 线碰到 A 线的文件了：是让它退回去，还是就这样？
   退回去：干净，但它可能确实需要那个功能。
   就这样：要 A 线后来补，可能要改两次。

2. A 线改的那个"任务主键改名"已经存了。
   要不要现在通知 B/C/D 把新改动并进去？
   现在并：它们手头的活会中断一次。
   等它们做完：可能攒出一堆对不上的地方。
```

## 4. 怎么描述"在做什么"

**不要照抄 commit message。** 把它翻成"这件事有什么用"。

| commit 原文 | 该怎么说 |
|---|---|
| `feat(botd): run_link 补齐三表 + kind 列` | 让系统能记住"这件事是谁派的、在哪个对话里做的、用的哪个 AI、开了什么工单" |
| `fix(botd): 迁移改成三段式` | 修的问题是：数据库升级到一半崩了，下次启动会再崩一次 |
| `feat(mcp): 30 个工具从契约解析` | 让"工具清单"只在一份文档里维护，改文档就生效，不用改代码 |
| `docs(plans): 汇报人工作规程` | 就是这份东西 |

**判据**：看完这句话，用户知道**这活儿解决了什么问题**，不只是"改了哪个文件"。

---

## 5. "麻烦"里只写有据可查的

| 能写 | 不能写 |
|---|---|
| D 线 6 小时没存东西，改完没存的文件也没变 | D 线可能遇到困难了 |
| C 线 3 项测试没过 | C 线应该快做完了 |
| B 线碰了 `botd/store.py`（15:20） | B 线有点乱 |

**判据：能不能说出文件、时间、具体现象。说不出来就不写。**

---

## 6. "要你定的"只写真的得人拍板的

| 能写 | 不能写 |
|---|---|
| A 线存了改名，要不要现在让其他三线把新东西并进来 | 要不要让 C 线加把劲（这是催，不是决策） |
| B 线说官方 SDK 装不上，是等网络还是先用旧的 | 用哪个库（文档里写着） |
| C 线需要一个 A 线还没做的接口，是先做假的还是等 | — |

**⚠ 文档里查得到答案的，别拿来问。**

---

## 7. 一句话

**像同事早上碰头跟你说的话：谁在忙什么、谁卡住了、有个事你得拍一下。**
**不是仪表盘，不是周报，不是汇报材料。**
