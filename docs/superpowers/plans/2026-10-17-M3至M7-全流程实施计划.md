## M3 第一个真 Agent：数据质量校验（2027-02 — 03）

**目标**：让 LLM 第一次真正进入链路，交付五类 Agent 里的**第一个**，并给出可复现、可追溯、有判据的归因能力。

**前置（进入条件）**

- M2 完成：两条真实数据源适配器、真实台账、来自真实样本的回放 fixture
- M1 的数据字典定稿（字段 / 单位 / 采样率 / 质控判据），且字段清单与 `StationReading` 对得上
- LICENSE 已定稿并登记 Notices（**已完成**，见 #36）
- spec §10 的五件事有结论，尤其是模型通道与算力（见下面的跨里程碑项）

**退出门槛**

- [ ] 具备一个能跑的质控 Agent：输入观测，输出归因 + 处置建议 + 置信度
- [ ] 每条结论都能挂回它调用过的工具输出，**无据结论被拒**
- [ ] 在标注样本集上跑出**归因准确率**，数字可被 `tools/audit_claims.py` 回源，并写进 README 与结题材料
- [ ] `harness/replay.py` 对该链路的分数可复现（同输入两次不劣化）
- [ ] DoD 六条全过（PR 合入 / skip 0 / selftest 0 / 数字回源 / replay 不劣化 / README 同步）

**风险与裁剪顺序**

- spec §8 与 §9 都写明「五类 Agent 不并行开工」，所以 **M3 只做这一个**。把它做扎实，是后面四类能便宜地实例化的前提。
- 若本地模型的复现性验证不通，按 spec §5 改用「多次运行的均值与极差」口径，**不得声称可复现而实际不可复现**。

### M3-0 模型通道落地与复现性验证（P0 · 看板 #50）

**为什么**：spec §5 定了双轨：本地模型走回归基线、API 走正式数字。但仓库目前只有 `FakeProvider`，真通道一个都没有。M3 是 LLM 第一次真正进链路，通道必须先落地，而且**先验证复现性** —— 否则 spec §3.3 那条「可复现」硬指标从第一天起就是空的。

**交付物**

| 项 | 落点 |
|---|---|
| 本地通道实现（Ollama 或 vLLM），默认 `qwen2.5:7b-instruct` | `src/fieldstation/agents/providers/` |
| `chat(messages, tools) -> response` 的 provider 抽象落地，配置全外置 | 同上 |
| 复现性验证脚本：固定 seed + `temperature=0`，同一输入跑多次比对 | `tools/` 或 `harness/` 下新增 |
| 实测记录与结论（可复现 / 不可复现→分布口径） | `harness/REPRODUCE.md` + 新增 ADR |
| 实测输出 | `logs/` |

**依赖**：无（可与 M2 并行）；需要一台能跑 7B 量化的机器，见跨里程碑项 `X-1`

**步骤**

- [x] 起本地模型服务，确认能返回工具调用
- [x] provider 抽象落地：换模型只改配置
- [x] 复现性验证：同 seed、`temperature=0`，跑 5 次比对结论
- [x] 若不可复现，写清改用「多次运行分布」的口径与理由，并记进 ADR
- [x] 记录本地通道的断网可用性

**验收**

- [x] 配置外置：换 provider / 模型是改配置，代码零改动（有测试）
- [x] `harness/replay.py` 不需要任何模型即可复现分数（回放已录制的 trace）
- [x] 复现性结论有实测证据，且**在接 API 之前**得出（spec §5 的硬要求）

**备注**

- 本地模型的规模要写进结题材料，不能含糊成「用了大模型」

### M3-2 归因结论的结构化契约（拒绝无据结论）（P0 · 看板 #52）

**为什么**：spec §3.3 的第 2 条硬指标是**可追溯**：每条结论都要挂回它调用过的工具输出，不允许无据结论。这要求结论本身是一个可校验的结构，而不是一段自由文本 —— 自由文本里「看起来有依据」和「真有依据」无法区分。

**交付物**

| 项 | 落点 |
|---|---|
| 结论契约：归因（故障类型 + 证据）+ 处置建议 + 置信度 | `src/fieldstation/agents/` 或契约模块 |
| 校验器：每条归因必须引用至少一条工具输出，引用不到的判无效 | 同上 |
| 负例测试：编造证据、引用不存在的工具调用、置信度越界 | `tests/` |

**依赖**：M3-1

**步骤**

- [x] 定契约（字段、取值域、必填项）
- [x] 写校验器与负例
- [x] 接进运行时：结论不合契约时**不许落盘为有效结论**
- [x] 确认 replay 能重新校验一遍已录制的结论

**验收**

- [x] 无据结论被拒（有负例测试）
- [x] 结论落盘后能被 replay 重新校验
- [x] 契约一旦定下，改动要走 ADR —— M4 的四类 Agent 都吃它

**备注**

- 这条是「不让 LLM 随便说话」的机械保证，不是提示词工程

## M4 研判 / 调度 / 归档 Agent + 知识库（2027-03 — 04）

**目标**：用 M3 已经跑通的运行时，把剩下四类 Agent 一次一类地实例化，并补上知识库。

**前置（进入条件）**

- M3 退出门槛全过 —— 尤其「新增 agent 只加配置、不改代码」这条确实成立
- 知识库的规程素材到手（质控规程 / 运维规程 / 设备手册）

**退出门槛**

- [x] 五类 Agent 全部可跑（质控在 M3，其余四类在此）
- [x] 知识库可用：SQLite + 全文检索，**不引向量库**（spec §8 的 YAGNI）
- [x] 高风险动作必须在人工审批门停下，放行与拒绝都落 trace
- [x] 每类 Agent 各有回放分数，且不比 M3 的基线劣化

**风险与裁剪顺序**

- **本计划最重要的一条决定**：spec §7 的里程碑表把 M4 写成「研判 / 调度 / 归档」三类，**五类里的「设备状态监测」在整张表里没有归属**。本计划把它放进 M4，于是 M4 要交付四类 —— 四个 Agent 挤在两个月里，是全程进度风险最大的一站。若必须裁，**按这个顺序从后往前裁**：
- 1. 先裁**数据管理归档**（最少判据依赖，最接近配套功能）
- 2. 再裁**运维任务调度**（工单与审批门可并入 M5 联调）
- 3. 再裁**设备状态监测**（其价值可由 M3 的质控 Agent + M5 看板部分覆盖）
- 4. **研判必须保住** —— 它是唯一直接对应「智能体替代人工判断」的核心交付
- 裁掉的必须在结题材料里如实写明，不许静默消失。

> 键 `<命名空间>/<条目>`，命名空间固定 `station` / `alert` / `order`（spec §4 的三个

> CAS 竞争恰好一个赢家、读者不会读到自相矛盾的值；另有「换一块板就什么都看不到」
> 钉住不存在隐藏状态。语义与边界（不做跨进程、不做就地修改、不做自动过期）写在
> `docs/operations/blackboard.md`。M5-1 的回放 harness 未声明黑板，基线与行为不变
> （当次 402 tests 全绿；M5 全部收口后为 411）。运行看板（M5-3）用 `upsert` 装载 +
> `snapshot()` 渲染，**不消费** `on_event`（实时看板等 M6 部署形态）。
