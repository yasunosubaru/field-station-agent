# ADR-009：七个引擎，一条总线；LangGraph 是唯一的循环

- 状态：**Proposed**（等负责人批准后改 Accepted）
- 日期：2026-11-04
- 关联：ADR-001（运行时选型）、ADR-008（界面底座）、issue #112–#120
- 结论一句话：**七层引擎各管一段，工具面只走 MCP；「会话循环」用 LangGraph 挂在界面底座的自定义模型接口（Pipe）上，全产品只有一个 agent 循环，不引第二个。**

---

## 1. 为什么会有七个引擎

0.2.0 是一条链：`Python 服务 ← Node 桥 ← 自写界面`。加界面的时候发现，真正缺的不是界面，
是**能力的边界**——「谁在调度」「谁在判断」「谁在存」「谁在驱动设备」混在一个 `tools/` 里，
每加一个功能就要在三个文件里改。

v2 把它们拆成七个引擎，每个引擎只回答一个问题，错也只错在一层：

| 引擎 | 回答的问题 | 现在是什么 | 新增/改动 |
|---|---|---|---|
| **E1 会话循环** | 人这句话该调哪个工具、怎么讲清楚 | 无（0.2.0 的循环在 `agents/orchestrator.py`） | **新**：LangGraph operator 图，挂成界面底座的自定义模型（Pipe，底座见 ADR-008） |
| **E2 Bot 引擎** | 没人问的时候谁在干活 | 无 | **新**：`botd` + Pydantic AI |
| **E3 领域编排** | 这批数据/这台设备到底有没有问题 | `agents/pipeline.py` 串行五阶段 | **改**：同一套阶段搬进 LangGraph StateGraph |
| **E4 数据引擎** | 数据从哪来、干不干净、怎么对比 | `ingest/` + `rules/` + `harness/` | **补**：批次、特征、数据集版本、DuckDB 列存 |
| **E5 存储** | 证据、台账、向量存在哪 | JSONL / SQLite 小规模 | **改**：SQLite（台账）+ DuckDB（分析）+ Chroma（向量） |
| **E6 知识** | 手册和规范怎么被检索到 | `agents/knowledge.py`（SQLite FTS） | **换**：LlamaIndex 摄取 + Chroma 检索 |
| **E7 设备** | 怎么真的动那台机器 | `cdp_driver` / `uia_driver` / `native_bridge` + 8 条流程 | **不动**（已验证，改它风险最高） |

## 2. 决定

### 2.1 只有一个循环

ADR-001 定的是「运行时用 LangGraph」。v1 的方案（OpenCode 当宿主 + LangGraph 当领域层）会出现
**两个循环**：一个会自己决定调什么工具、一个也会。两套上下文、两套审批、两套 token 账，
而且它们互相不知道对方判了什么。

**所以：不引 OpenCode，不引 Claude Code Best。** LangGraph 同时承担两件事：

- **E1 operator 图**：一回合内决定「调哪个工具 / 转给哪个子图 / 直接回答」，管叙述与澄清；
- **E3 领域图**：五阶段状态机，管判据、结论契约、闸门。

两张图是同一条流水线的两段：E1 只会调用 E3 暴露的工具，**E1 不许自己下领域结论**。
这条是硬约束，比任何实现细节都重要——它保证「模型归因 / 规则裁决 / 人工审批」不被绕开。

### 2.2 工具面只走 MCP

所有能力对「循环」暴露成 MCP 工具（Streamable HTTP）：底座支持原生 MCP 就直连，
不支持就用 `mcpo` 这类代理转一层——传输层可换，工具表只有一份。

- 领域：`fsa.station.health` / `fsa.qc.evaluate` / `fsa.fault.diagnose` / `fsa.work_order.create`
- 编排：`fsa.pipeline.run` / `fsa.pipeline.status`
- 数据：`fsa.data.batches` / `fsa.data.quality` / `fsa.dataset.version`
- 知识：`fsa.kb.search`
- 设备：`fsa.workflow.run` / `fsa.workflow.status` / `fsa.workflow.gate` / `fsa.suite.launch`

规则：**工具名、schema、错误语义在一处注册**（`src/fieldstation/mcp/`），
E1/E2/E3 都从同一张表取；不许某个引擎私开一条「直接 import 另一个引擎」的快捷方式。

### 2.3 Bot 引擎用 Pydantic AI，不用 Letta

「AI 管 AI」要的是：Supervisor 拆活 → worker 各自带工作区/记忆/模型/沙箱 → 结果回写 → 人能复盘。

- **Pydantic AI**：ADR-001 里本来就是备选，类型化工具、结构化输出、可测试；
  正好用来定义 bot 的输入输出契约（拆出的每一步必须带工具白名单与验收条件）。
- **不引 Letta**：它自带一套 agent server + Postgres，等于在我们的壳里再放一个壳。
  常驻调度、队列、沙箱、记忆这些「运行时」的事由 `botd` 自己做，只借 Letta 的记忆模型思想。
- **记忆**：短期=会话；长期=`bot_memory` 表 + Chroma 检索；经验=失败的 job 与它的失败分类。

### 2.4 存储只留三种，都是嵌入式

| 库 | 装什么 | 为什么是它 |
|---|---|---|
| SQLite | 台账、会话映射、bot 状态、工单、审批、job | 与界面底座同库同备份（同栈时）；事务；单文件 |
| DuckDB | 观测数据、质控结果、特征、数据集版本 | 列存，直接读 Parquet，零服务 |
| Chroma | 知识库向量 | 嵌入式，单文件；底座自带就复用，避免两份向量 |

**没有 Redis / Kafka / Postgres / 向量服务。** 这条与 ADR-007 的「三人团队、离线可复现」一致。

## 3. 边界与失败语义

| 情况 | 谁负责 | 结果 |
|---|---|---|
| 模型调了不存在的工具 | MCP 注册表 | 返回 `unknown_tool`，E1 必须改口，不许编结果 |
| 工具超时 | 该引擎 | `timeout` + 证据保留；E1 只能说「没查成」 |
| 结论缺证据 | E3 结论契约 | `ConclusionRejected`，该阶段不发布 |
| 高风险动作 | E7 闸门 | 停在 `waiting_approval`，UI 显示审批卡，人不批就不动 |
| bot 越界写文件 | E2 沙箱 | 拒绝并记一条 `sandbox_denied` |
| 上游套件改了控件文字 | E7 | `GuiUnavailable` + 截图，转人工；**不许猜着点** |

## 4. 代价

1. **E1/E3 要自己把循环打磨好**（流式、工具重试、上下文压缩、取消）——这是不引现成宿主循环的代价，
   约 2–3 周，但换来「一个循环 + 完全可控的 trace」。
2. **依赖变多**（langgraph / pydantic-ai / duckdb / llama-index / chromadb）→ 只允许在
   `graph/`、`botd/`、`data/`、`kb/` 四处引第三方；`agents/`、`rules/`、`store/`、`tools/` 仍是纯标准库。
3. **`pipeline.py` 保留**为降级路径与对照基线：没装 langgraph 时链路照跑，CI 不装依赖也不会红。

## 5. 未采用

- **OpenCode 当 E1**：247 MB 单二进制 + 第二套循环语义；换来的能力（多文件编辑、git 感知）
  我们一次都用不到。
- **Claude Code Best 当 E1**：无 LICENSE，逆向 Anthropic 产品，不能进结题材料。
- **两个循环并存**（v1 方案）：审批、token、trace 三本账，评审一问就露。
- **向量库上服务**（Qdrant/Milvus）：单机便携不需要。
