# ADR-009：引擎分层 —— 双 Agent 运行时、Bot 三组件、数据双引擎

- 状态：**Accepted**（2026-11-04 负责人确认：两个运行时都做且互不依赖；DBOS/LangGraph/Letta 都用；数据两套引擎并存）
- 日期：2026-11-04
- 关联：ADR-001（运行时）、ADR-008（壳与四视角）、`docs/spec/2026-11-04-v3-四视角双运行时.md`
- 结论一句话：**七个引擎各管一段；E1 有两个互不依赖的运行时；E2 由 DBOS/LangGraph/Letta 各持一类真相协作；E4 是同一份 Parquet 上的两个查询引擎。**

---

## 1. E1 会话循环：两个运行时，互不依赖

### 决定

同时实现两个 Agent 运行时，**各自都能独立完成全部 agent 任务**，任一缺失不影响另一个：

| | A · OpenCode（OpenChamber 源码） | B · Claude Agent SDK（官方） |
|---|---|---|
| 循环 | OpenCode 运行时 | Agent SDK 的 agent loop |
| 接 deepseek | 原生 OpenAI 兼容 | 经 `tools/anthropic_shim.py`（Anthropic Messages ↔ OpenAI） |
| 不装 shim 时 | — | 用它自带的模型通道，任务照样能做完 |
| 会话状态 | 自己的 | 自己的 |
| 工具面 | 各自直连同一个 MCP 服务 | 同左 |

### 硬约束（"同等地位"的操作定义）

1. **不许有共同前置**：任何一个运行时都不许以另一个、或以 shim 为启动条件；
   shim 是 B 接 deepseek 的**适配件**，缺了只影响 B 选不选 deepseek，不影响 B 能不能干活。
2. **不许共享状态**：各自持有会话/线程；切换运行时 = 换后端，不搬运上下文。
3. **不许互相代理**：两边各自连 MCP；任何一方不能通过另一方调工具。
4. **失败隔离**：一方崩溃，另一方照常；UI 明示"当前运行时不可用"，**不自动切换**（切换要人点）。
5. **特化只写一份源**：`agents/fsa-ops.yaml`（工具白名单、输出契约、权限）为唯一源，
   分别生成 OpenCode 的 agent 定义与 Claude 的 `AgentDefinition`；两份产物由 CI 校验同源。

### 边界

两个运行时都**不许自己下领域结论**——结论只能来自 E3。它们只负责：选工具、组织语言、澄清。

## 2. E2 Bot 引擎：DBOS + LangGraph + Letta 各持一类真相

### 所有权（先定这个，才不会有四本账）

| 组件 | 拥有 | 只写这里 | 不碰 |
|---|---|---|---|
| **DBOS** | 执行真相：何时该跑、跑到第几步、重试几次 | 自己的 workflow/step 表（SQLite） | 判业务、写记忆、写工单 |
| **LangGraph** | 推理真相：怎么拆、走哪个分支、结论与证据 | checkpointer + `trace.jsonl` | 定时、跨月调度 |
| **Letta** | 记忆真相：bot 是谁、记得什么、经验是什么 | memory blocks / archival | 执行工具、决定下一步 |
| **领域台账** | 业务真相：工单、审批、结论、产物 sha256 | 我们的 SQLite 表 | 存调度状态 |

四者用 `run_link(task_id ↔ thread_id ↔ agent_id ↔ work_order_id)` 串起来；
UI 上任何一条记录都能一次拉全"为什么跑 / 怎么想的 / 记得什么 / 最后做了什么"。

### 调用链（外层永远是 DBOS）

```
DBOS workflow bot.task.run(task_id)
 1  letta.recall(agent_id, task)                → 记忆块
 2  langgraph.invoke(plan_graph)                → 结构化计划（每步带白名单+验收条件）
 3  每步 enqueue 子 workflow（并发/限流由 DBOS 队列）
 4  遇到写动作 → LangGraph interrupt → DBOS durable sleep → 人批 → signal 恢复
 5  letta.remember(agent_id, 结果/失败原因/证据号)
 6  写台账 + 通知
```

三条纪律：**只有 DBOS 管时间；只有 LangGraph 管判断；Letta 只出现在首尾。**

### 交互层（人与"正在跑的 bot"）

编队台的交互抽屉 = **任务树 + 事件流 + 三种受控干预**，不是聊天窗口的复制品：

| 形态 | 内容 |
|---|---|
| 任务树 | Supervisor 为根，每个 worker 一步；点开看输入、工具调用、证据、耗时 |
| 事件流 | 派发 → 执行中（工具/耗时）→ 停闸门 → 已批准 → 完成；消息是树上的注释 |
| 干预 | 暂停/继续（任何人）、改参重试（记审计）、接管该步（需审批） |
| 对话 | **可以和大 bot 自由对话**；也可下钻到某个小 bot 的任务步直接对话/接管 |

干预指令进 `intervention` 表，由 DBOS 在**步骤边界**消费（不在工具执行中途强插）。

### 降级梯度（任一层可换，不牵动其他层）

1. Letta 不可用 → 记忆降级为 `bot_memory` 表 + Chroma，任务照跑（标 `memory_missing`）；
2. DBOS 不可用 → 退 APScheduler + 队列表（丢 exactly-once，明确告知）；
3. LangGraph 不可用 → 退 `pipeline.py`（已有），判断变简单，验收分数如实下降。

## 3. E4 数据：一份真相，两个引擎

| | 默认（轻量） | 高性能 |
|---|---|---|
| 组成 | Parquet + DuckDB | **ClickHouse 单机**（随包）+ 同一份 Parquet |
| 体积 | 0（已有） | +250–300 MB 解压 |
| 适用 | ≤50 亿行、日常、演示 | 十亿级多维聚合、秒级看板 |
| 切换 | 设置里一键；原始层不重建，只重建聚合 | 同左 |

- **唯一真相是 Parquet 分区**（`station/date/hour`），两个引擎都只是它的读端，不存在两份数据；
- **能力探测**：启动查 ClickHouse 二进制与端口；起不来自动回落 DuckDB，并在数据台顶部显示
  "高性能引擎不可用，已回落"，**不许静默**；
- **同一套基准 SQL**（20 条，W0 定义）两边都跑，谁慢谁错一目了然；
- 上层只写一种 SQL 方言（DuckDB 兼容子集），方言差异由适配层翻译。

## 4. 其余引擎（角色不变）

| 引擎 | 定位 |
|---|---|
| E3 领域编排 | LangGraph 五阶段；**唯一允许产领域结论的地方**；`pipeline.py` 为降级路径 |
| E5 存储 | SQLite（台账/会话/bot/审批）+ Parquet（观测）+ Chroma（向量） |
| E6 知识 | LlamaIndex 索引「元数据卡 + 手册 + 报告」；Text-to-SQL 走 E4；答案必须带出处 |
| E7 设备 | CDP / UIA / native + 8 条流程 + 闸门 + audit（已有，不动） |

## 5. 代价

| 项 | 代价 | 处置 |
|---|---|---|
| 双运行时 | 两套装配、两套事件映射、打包两份运行时 | 契约先行（一份事件协议），CI 校验同源特化 |
| 三组件 | 三套依赖、三处状态 | `run_link` 单一耦合点 + 降级梯度 |
| 双数据引擎 | +300 MB、方言差异 | Parquet 单一真相 + 基准 SQL + 自动回落 |
| 总量 | 目标 ≤1.6 GB（原 1.3 GB） | W0 实测；超了先砍 ClickHouse 之外的体积 |

## 6. 未采用

- 只做一个 Agent 运行时（负责人要求两个都做、之后评估再定）；
- 用一个适配层套两个后端（会造成共同前置，违反"互不依赖"）；
- 让 Letta 承担调度（会长出第三个决策者）；
- 让 LangGraph 自己定时（它不管时间）。
