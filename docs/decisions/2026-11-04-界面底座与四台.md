# ADR-008：四个台不再自己写界面 —— 底座三选一（待拍板）

- 状态：**Proposed / 待拍板**（2026-11-04 修订：上一版直接写了「用 Open WebUI」，越权，已降级为候选）
- 日期：2026-11-04
- 关联：ADR-001（运行时）、ADR-007（四层口径）、ADR-009（七引擎）、issue #112–#130
- 结论一句话：**四个台都长在成熟框架上，不再手写通用界面；但「哪个框架」还没定，三个候选见 §4。**

---

## 1. 要解决的问题

0.2.0 的界面是我们自己写的（`逆向/04_重实现/packages/app/src/web/`）。它证明了两件事：
能把事做出来；**再往上加台面会失控**——每多一个台，就多一套自己的布局、表格、空态、
表单、弹窗、权限与审计显示，全部要自己维护。

负责人的要求：**四个台都要有面向人的界面，别自己写，用成熟框架，在上面深度特化。**

这条要求落在两层，别混：

| 层 | 「用成熟框架」的意思 | 我们不写的 | 我们必须写的 |
|---|---|---|---|
| **台面**（人机界面） | 用现成产品的页面/组件做骨架 | 会话、流式、Markdown、文件、知识库、用户与权限、管理后台 | 四个台的**领域视图**（设备、工单、流程、证据、评测） |
| **引擎**（能力层） | 用现成运行时做骨架 | agent 循环、RAG、列存、调度 | **领域判据、五阶段契约、设备通道、证据链** |

ADR-009 已经把第二层定死（LangGraph / LlamaIndex / DuckDB / Pydantic AI / CDP）。
本文只管第一层：**台面的底座**。

## 2. 不可退让的约束

1. 单 EXE、离线可跑、断网不瘫；
2. 三个台面尽量开箱即用，只有「专业台」允许自建（它是显示层）；
3. 不许出现两套设计系统、两套权限模型；
4. 许可干净：引入的框架保留署名，没有 LICENSE 的代码不进仓库；
5. 体积可控（目标 ≤1.3 GB 压缩后）。

## 3. 候选（只从负责人给的那份清单里选）

### A · Open WebUI

- 形态：Python/FastAPI + SvelteKit，默认 SQLite；自带 Chat / Workspace（模型·知识·提示词·工具）/ Admin；v0.6.31+ 原生 MCP（Streamable HTTP）
- ✔ 后端与我们的引擎**同栈**（都是 Python 3.11），可以同进程挂载；数据库默认就是 SQLite
- ✔ 三个台面（会话 / 知识 / 管理）开箱即用，样式统一
- ✘ 依赖重：解压后估 400–500 MB（fastapi / sqlalchemy / uvicorn / chromadb / onnxruntime）
- ✘ 品牌条款：≥50 用户/30 天不得改标识 —— 我们单机单用户够用，但仍保留署名并声明是 fork
- ✘ 它是"聊天为主"的产品，运维台的**信息密度**要自己加（这正是专业台要自建的原因）

### B · LibreChat / LobeHub

- LibreChat：MIT、React、Agents 面板齐全，但要常驻 MongoDB
- LobeHub：界面最好看、Agent 与知识库最全，但 2.0 后强制 Postgres
- ✔ 成熟度与观感在 A 之上
- ✘ 多一个数据库服务 → 便携单 EXE 里再塞一个 daemon，与「插上就能用」冲突
- ✘ 包的体量与升级路径都比 A 重

### C · 自己写（沿用 0.2.0 三栏）

- ✔ 体积最小、完全可控、已有 828 项测试与验收清单
- ✔ 不引新许可、不跟上游漂移
- ✘ 每个台都要自己写布局/表格/空态 —— **正是这次要解决的问题**
- △ 折中形态：只借组件库（shadcn / Tremor / 现成的图表库），页面仍自己写

## 4. 决定（待填）

| 判据（权重） | A | B | C |
|---|---|---|---|
| 三个台开箱即用（最高） | 强 | 强 | 弱 |
| 与 Python 引擎同栈（高） | 强 | 弱 | 中 |
| 单 EXE / 离线（高） | 中（依赖重） | 弱（要 DB 服务） | 强 |
| 观感与信息密度（中） | 中 | 强 | 弱（现状） |
| 体积（中） | 中 | 弱 | 强 |
| 许可干净（中） | 中（品牌条款） | 强 | 强 |

**建议**：目标「四个台都像样 + 不再造第二套后端」→ **A**；
目标「界面最好看、可接受多一个 Postgres」→ **B**；
目标「体积与可控优先」→ **C + 组件库**。

**这一栏等负责人勾选后再改 Accepted。** 在勾选之前，任何实现工作都不以某个框架为前提。

## 5. 四条候选都要遵守的规矩

不管最后选哪个，下面四条不变：

1. **只有专业台允许自建**，而且它只做显示：读 E7 / E5，不自己写数据、不自己发写动作；
2. **领域视图必须落在框架的页面体系里**（同一套导航、主题、权限），不许另起一套 SPA；
3. **不许嵌两层壳**：把 A 或 B 整包塞进我们的壳再套一层，等于两套 UI + 两套权限，明确禁止；
4. **许可与署名**：引入谁就保留谁的 NOTICE，并在文档里声明「fork / 非官方」。

## 6. 怎么验证这个决策成立

选定之后，用同一张验收表量：

1. 四个台都能进，且导航/主题是同一套；
2. ① 会话台能跑通「问健康度 → 调 `fsa.station.health` → 带证据回答」；
3. ③ 专业台能显示 Manage 与 Workflows 的真实数据；
4. ④ 知识库能检索到入库的 NovAtel 帮助原文；
5. ② bot 列表能看到至少 2 个 bot 与今天跑过的任务；
6. 断网可用；从干净机双击起得来。

任一条不成立，回到本文改决策，不在代码里打补丁。
